# 税務シミュレーター UI層 設計書（第1版）

作成日: 2026-08-29
対象: 仕様書 §5・§6・§8-1・§13・§22・§52・§57〜§59・§61・§61-1・§67
前提: 4サービス（validate / simulate）は §7-1 契約で完成済み（deferred-items.md 参照）

## 1. この文書の位置付け

### 1-1. 決めること

- 配信・ビルドのアーキテクチャ（どうやってブラウザで動かすか）
- ランタイムの構成と §67 のレイヤ分離の守り方
- 入力→Wire→validate→simulate→結果表示の画面側の流れ
- §57 のセキュリティ制約・§61-1 のアクセシビリティ制約の実装方針
- 実装順序と公開ゲートの連携

### 1-2. 決めないこと

- 視覚デザインのトーン・配色・文言の最終形（公開前に税理士承認 §52。E-1）
- 相談フォーム連携（§57-3。別仕様の承認まで公開しない）
- 追加質問の上限数（§5。ユーザビリティテスト後に設定として版管理）

## 2. 配信アーキテクチャ

### 2-1. URL と静的ページ

- 仕様書 §8-1 等の固定URL: `/tools/hojinnari-simulator/`・`/tools/shohizei-simulator/`・`/tools/sozokuzei-simulator/`・`/tools/yakuin-hoshu-simulator/`
- 各URLは既存のサイトビルド（templates/pages）で生成する**静的ページ**。ページはタイトル・説明・免責・構造化データ（§52-2）と、アプリのマウント先および1本のスクリプトタグだけを持つ
- 4ページはすべて**同一のバンドル**を読み込み、ページ側の `data-simulator` 属性で起動ツールを選ぶ

### 2-2. 単一SPAランタイム（§57-1 の要請）

- §13 の④→①受け渡しは「同一SPAランタイムのメモリ内オブジェクト」で行う（§57-1）。このため4ツールは1つのアプリとしてバンドルし、ツール間遷移は History API の pushState（**URLに財務データを載せない**・§61-1）で行う
- 直接アクセス（リロード含む）はそのURLの静的ページが同じアプリを起動する。リロードで受け渡しが失われることはUIで説明する（§57-1）
- Handoff は §13-1 の型のとおりメモリ内オブジェクトで検証付きに実装し、直列化しない

## 3. ビルド

### 3-1. 自前バンドラ（依存ゼロ）

- 新規パッケージは**追加しない**。`scripts/build-simulator-bundle.js`（新設・Node標準APIのみ）が CommonJS モジュール群を `function(module, exports, require)` ラップ＋ミニリゾルバで1ファイルへ決定的に連結する
- 理由: §57-2 は依存固定・脆弱性検査・サプライチェーンを要求する。税務YMYLでは「ビルドツール自体が注入経路」になるリスクを依存ゼロで消すのが最も強い。minify はしない（可読な配信物は §52-1 の検証可能性にも資する）。サイズが問題になった場合のみ esbuild（完全固定版）を再検討する
- 出力: `assets/js/tax-simulator.<contenthash>.js`（IIFE）。ページ生成時にファイル名とSRI（sha384）をスクリプトタグへ埋め込む

### 3-2. マスターの同梱とハッシュ検証（§57-2）

- Node専用APIに依存するのは `rounding.js`（fs/path）と `snapshot.js`（fs/path/crypto）の2ファイルのみ。両者へ「データ供給源の注入点」を追加し、Node では従来どおりファイルから、ブラウザではビルド時に生成する**同梱データモジュール**（全マスターJSON＋丸め規則＋snapshotId/Hash）から読む。エンジン・サービスのコードは一切変えない
- ビルド時: 同梱データから `computeSnapshotHash` を再計算し、ファイル版スナップショットと一致しなければビルド失敗
- 実行時: 起動時に WebCrypto（`crypto.subtle.digest`）で同梱データのSHA-256を再計算し、埋め込みハッシュと一致するまで計算機能を有効化しない。「依存ライブラリとマスター配信物はバージョン・ハッシュを固定し、検証失敗時は計算エンジンを起動しない」（§57-2）をこの2段で満たす
- BigInt はモダンブラウザ全対応。ポリフィルは置かない（非対応環境では起動せず案内を出す）

### 3-3. 公開ゲート連携（§52-3）

- サイトビルドは `masters:gate` の判定を読み、**公開不可のシミュレーターのページを生成しない**（既存ページがある場合は「準備中」ページへ差し替える）。ゲート緑が配信の前提条件になる

## 4. ランタイム構成（§67）

```
UI（本設計書の範囲: 画面・状態・表示整形のみ）
↓ Wire形式の入力 / SimulationResult
Simulator Service（実装済み・変更しない）
↓
Tax Engine → Tax Master（実装済み・変更しない）
```

- UI層に税計算・税率・金額定数を書かない（§67・§3-1）。表示用の丸め・桁区切りも「表示整形」に限り、計算値там改変しない
- UIコア（共通部品）:
  - `dom.js` — `createElement` ベースの要素生成。外部由来テキストに `innerHTML` を使わない（§57-2）
  - `store.js` — ツールごとの状態（入力値・STEP位置・結果）。メモリ内のみ（§57-1）
  - `router.js` — pushState 遷移とツール起動。URL・履歴へ財務値を入れない
  - `forms.js` — 金額入力（§61-1: `inputmode="numeric"`・文字列入力・桁区切りは表示のみ・IME中は整形しない・確定値の「1,000,000円（100万円）」確認表示・上限下限の事前明示）、TriState、選択肢、期間入力
  - `a11y.js` — `role="status"` / `role="alert"` の通知、結果見出しへのフォーカス移動（§61-1 の描画分離規則を内蔵）
  - `analytics.js` — §58 の許可5イベントのみ送れる型付き関数。金額を載せるコードが書けない形（引数に数値を受けない）にする

## 5. 入力UI

### 5-1. かんたん／詳細とSTEP

- トップレベルの `precision` 切替（設計書 §11-2）。かんたんは §9・§16 の最小項目、詳細は全項目
- STEPは「現在のSTEP / 現時点の総STEP数」をテキストとプログラムの両方で表示（§61-1）。「戻る」で入力値を失わない。追加質問で総数が増えたら増えた旨を通知
- 入力済みの値を別STEPで再入力させない（WCAG 3.3.7）

### 5-2. Wire組立と検証

- フォーム値は**Wire形式**（Decimal文字列のMoney等）で組み立て、`service.validate` へ渡す。ok:false の `fieldPath` を入力欄へ対応付け、ページ上部のエラー要約（該当欄リンク付き）と各欄の `aria-describedby` の両方で示す（§61-1・WCAG 3.3.1/3.3.3）
- validate ok → メモリ内表現で `service.simulate`。CalculationContext はUIが組み立てる（年・自治体選択・スナップショットIDは同梱データから）

### 5-3. blocked → 追加質問（§5 の判定順）

- サービスの blocked 理由コードを**質問文カタログ**（ツール別・コード→日本語の質問・入力欄種別）で画面の追加質問へ変換する。カタログに無いコードは原文メッセージ＋専門相談導線で表示（取りこぼしても無言にしない）
- §5 の1〜4（blocked／追加質問／範囲表示／partial）の順序を崩さない。範囲表示は `summary.range` があるときだけ
- カタログのコード体系は `ExcludedItem.code`・警告コードと同じ台帳で管理し、§5 の「計算範囲: 計算済み項目数 / 対象項目数」の分母カタログを兼ねる

## 6. 結果UI

- **結論カード**（§6）: 断定表現を使わない定型文（「本シミュレーションの入力条件では〜」）。§11 の併記事項（個人自由資金・法人留保・税社保合計・設立コスト前後）と「法人内部に残る資金は〜」の注意を必ず表示
- **比較表**（§11）・**方式比較**（§22: eligible の行だけ税額、対象外の行は理由）・**③の申告要否**（税額0円≠申告不要の文言を明示）
- **計算範囲表示**（§5）: 計算済み/対象項目数・直接入力/制度既定値/推定値・除外項目・結果状態。「概算精度: 標準」のような一語評価は出さない
- **警告**（§61）: level 別の表示。色だけで区別しない（§61-1）
- **前提・出典**: assumptions・sources・calculationVersion・masterSnapshotId・法令基準日を結果下部と印刷物に必ず出す（§7・§59）
- **印刷**（§59): ブラウザ印刷CSS。入力フォーム・相談用個人情報を含めない。基準日・前提・除外・警告・版・スナップショットID・ページ番号を出す
- **入力をクリア**: 全STEPと結果画面に設置。メモリ・印刷用DOM・クリップボード一時値を破棄（§57-1）
- グラフは第1版では**任意**（④のMODE A候補推移のみ検討）。載せる場合は §61-1 のグラフ規約（代替表・境界行の選定規則明文化・forced-colors）を満たすまで出さない

## 7. セキュリティ（§57）

- 計算はブラウザ内で完結。金額・入力値をURL・Cookie・localStorage・sessionStorage・IndexedDB・`window.name`・`document.title`・DOM属性・解析へ入れない
- シミュレーターページには既存サイトの汎用スクリプト（assets/js/main.js 等）を読み込まない。読み込むのは検証済みバンドル1本だけ
- Netlify の `/tools/*` ヘッダで CSP を配信する（§57-2 の列挙どおり）:
  - `default-src 'none'` 起点。`script-src` はバンドルのハッシュ（SRI と同源）、`style-src` は自己配信CSS、`connect-src`/`form-action` は自社オリジンのみ、`object-src 'none'`・`base-uri 'none'`・`frame-src 'none'`・`frame-ancestors` 制限
  - `Referrer-Policy: no-referrer`・`Permissions-Policy` で不要APIを無効化
- `sendBeacon`・`fetch keepalive`・WebSocket・`RTCPeerConnection`・`<a ping>`・preconnect/prefetch へのURL値埋め込み・`window.open` クエリをシミュレーター画面で使わない
- Service Worker を `/tools/` パススコープに登録しない。既存SWがある場合は当該パスをキャッシュ対象と navigationPreload から除外
- 金額欄はフォーム自動補完を無効化。BFCache・ページ復元時に金額状態をクリア（`pageshow` の persisted 判定）
- ソースマップは本番へ出さない。デバッグログ禁止。ブラウザ拡張・共用端末・画面共有への注意書きを利用上の注意へ記載

## 8. Analytics（§58）

- 許可イベント: `simulator_view` / `simulator_start` / `simulator_complete` / `simulator_mode` / `simulator_cta_click` のみ。送信先は自社オリジン（既存のサイト解析基盤）
- ペイロードは型で許可リスト化（ツール名・モード・結果状態のみ。金額・自由記述・エラーメッセージ・金額帯を載せる引数が存在しない設計）。テストで担保

## 9. アクセシビリティ実装規約（§61-1 の要点）

- WCAG 2.2 AA / JIS X 8341-3 目標。キーボードのみで入力・計算・戻る・印刷が可能
- 計算完了は結果見出し（`tabindex="-1"`・結果状態と対象期間を含む文言）へのフォーカス移動を主通知とし、ライブ領域は計算中と停止のみ。挿入とフォーカス移動を同一描画で行わない。blocked とエラーは `role="alert"`（同一操作1回）
- 長い走査（④MODE A/B・③二次相続（将来））は非同期チャンク実行＋処理中表示＋キーボード操作可能な中止。中止時は途中結果を結論に残さない
- 再計算時は旧結果を破棄してから同じ見出しへフォーカス。旧新併記しない
- 色以外の手段（文字・形）で有利不利・可否・警告レベルを表現。400%拡大・幅320pxリフローで結論カード等は二方向スクロールを要求しない
- 受入は自動チェックのみで合格とせず、キーボードのみ・スクリーンリーダー1種・200%拡大・320pxリフローの手動確認をチェックリスト化する（§61-1 末尾）

## 11. 決めた背景（要点）

- **依存ゼロの自前バンドラ**: サプライチェーンリスクの排除（§57-2）と、この規模（エンジン＋サービス約450KB・マスター約1.3MB、gzip後合計約3〜400KB想定）ならツール不要と判断。遅延読み込みはツールページのみなのでサイト本体に影響しない
- **1バンドル4ページ**: §57-1 の「同一SPAランタイム」と §8-1 の固定URLの両立。財務データをURLへ載せずに画面間受け渡しできる唯一の素直な構成
- **フレームワーク不採用**: 依存ゼロ方針の一貫。§61-1 の細かなフォーカス・通知制御は素のDOMの方が確実に制御できる

## 12. 公開・停止の運用手順

### 公開

1. 税理士による計算基準・表示文言・第1版対象外項目の確認を完了し、`publish-config.json` の3日付を確定する。
2. `masters:validate`、`masters:test`、対象ツールの `masters:gate`、`input-types:check`、`simulator:bundle`、`build`を順に実行する。
3. 対象ツールの `enabled` を `true` にしてページ生成を有効化する。検索公開は別段階とし、承認済み本番URLだけ `indexable` を `true` にする。
4. デプロイ後、canonical、noindex、監修表示、免責、JSON-LD、SRI、`simulator-status.json` のsnapshotIdを本番で確認する。

### 緊急停止

1. 停止対象ツールの `enabled` を `false` にする。誤った結果を表示していた場合は `indexable` も `false` にし、訂正履歴へ影響した計算バージョン、マスタースナップショットID、影響期間、再計算の要否を記載する。
2. `npm run build` を実行し、`simulator-status.json` で対象ツールが無効になったことを確認してデプロイする。
3. NetlifyのCDNキャッシュを無効化（Purge cache）し、ページHTMLと `simulator-status.json` の再検証を促す。ブラウザ側は `cache: no-store` でstatusを取得し、前回値では続行しない。
4. 本番URLを新しいブラウザセッションで開き、計算UIが描画されず、停止理由の区分と相談窓口が表示されることを確認する。既存のService Workerがある場合は対象パスをキャッシュ・navigation preloadから除外する。

再開時は旧マスターを自動で戻さず、最後に承認済みで対象期間が一致するsnapshotIdを明示的に選び、公開手順を最初から実施する。
