## 1. 設計方針

### 1-1. 既存資料の活用

親プロジェクト `hp-vlog/data/nta-sources/` に以下の一次資料が取得済み。

| 資料種別 | 件数 | 最終取得 |
|----------|------|----------|
| タックスアンサー | 672件 | 2026-08-01 |
| 質疑応答事例 | 1,550件 | 2026-08-01 |
| 基本通達 | 3,596条文 | 2026-08-21 |

これらをマスターデータの**一次資料源**として使用する。ただし：

- タックスアンサーの本文テキストから値を直接転記しない（§50-1 の取込・二者確認フローを通す）
- タックスアンサーの `law_version` は「令和7年4月1日現在法令等」であり、令和8年度改正を反映していない項目がある
- `tax-law-changes.js` の改正データおよび §50-2 の重要根拠台帳の資料で補完する
- 既存の `html_hash`/`fetched_at` は `SourceReference` のメタデータに流用可能

### 1-2. マスターの範囲

仕様書 §3-1 が定める11マスターテーブル＋補助テーブル。

## 2. 共通フィールド（全マスターレコード共通）

仕様書 §3-1 に基づく。

```jsonc
{
  // === 識別 ===
  "record_id": "IT-2026-BRACKET-03",
  "master_name": "income_tax_master",

  // === 適用期間（税目ごとの時間軸） ===
  "tax_or_insurance_type": "income_tax",
  "jurisdiction": {
    "country": "JP"
    // 必要に応じて prefectureCode, municipalityCode, healthInsurerCode
  },
  "effective_from": "2025-01-01",
  "effective_to": "2025-12-31",
  "applies_to_period_start_from": null,
  "applies_to_period_start_to": null,
  "applies_to_transaction_from": null,
  "applies_to_transaction_to": null,

  // === 値（型は個別スキーマで定義） ===
  "value": { /* マスター固有 */ },

  // === 計算順序・端数 ===
  "calculation_order": 1,
  "rounding_rule_id": "R-TRUNC-1000-BASE",

  // === 出典・検証 ===
  "source_document_id": "NTA-TA-2260",
  "source_locator": "計算方法・計算式 > 所得税の速算表 第3行",
  "source_hash": "b3c03d163fa7ee33870b3c96a9b07ba084c2fb25a56afe5ff75b7117808c2171",
  "verified_at": null,
  "verified_by": null,
  "promulgated_at": "2025-03-31",
  "as_of_date": "2026-08-23",

  // === 状態管理（§48） ===
  "legal_status": "effective",
  "data_review_status": "unverified"
}
```

### legal_status 値集合

| 値 | 意味 | 本番計算への投入 |
|----|------|-----------------|
| `draft` | 未公表の案 | 不可 |
| `announced` | 大綱・法案として公表、未成立 | 不可 |
| `enacted` | 成立・公布済み、適用開始前 | 対象期間の確認後のみ可 |
| `effective` | 対象期間に適用中 | 可 |
| `expired` | 適用終了 | 過去の期間のみ |
| `repealed` | 廃止 | 不可 |

### data_review_status 値集合

| 値 | 意味 | 本番公開 |
|----|------|---------|
| `unverified` | 未検証 | 不可 |
| `single_checked` | 一者確認済み | 不可 |
| `double_checked` | 二者確認済み | 不可 |
| `approved` | 税理士承認済み | 可 |
| `blocked` | 不整合等で停止 | 不可 |

## 6. 年次更新への対応

税法と社会保険料率は毎年変わる。このシステムは今年だけ使うものではないので、
「変わったことに気づく」仕組みを制度側に置く。

### 6-1. 方針：検知は自動、値の入力は人

既存の `check-tax-reform-outline.js` と同じ考え方を採る。

| 自動でやること | 人がやること |
|---|---|
| 出典が変わったことの検知 | 原文を読んで改正内容を判断する |
| 対象年度のレコードが無いことの検知 | 新しい金額・段階・境界の入力 |
| 告示時期の予告 | 二者確認と税理士承認 |

**値を自動で書き換えてはいけない。** タックスアンサーの表はHTMLの `rowspan`/`colspan` でセルが結合されており、
テキストに平坦化すると列の対応が失われる（No.1199 の R7/R8/R9 の4列がまさにそれ）。
機械が読み違えた金額がそのまま本番計算に載ると、間違いに気づく機会が無くなる。

### 6-2. 3層の検知

**層1：出典の変更検知**

マスターの `source_hash` と、国税庁ソースDBの現在の `html_hash` を突き合わせる。
ズレていれば出典が更新されている。

既存の `crawl-nta-sources.yml`（毎月1日）がタックスアンサー672件のhashを更新するので、
その結果を使うだけでよく、追加のクロールは要らない。

**層2：年度カバレッジの確認**

出典台帳の `coverage_basis` が `calendar_year` / `fiscal_april` のマスターについて、
対象期間を覆う「使えるレコード」（`blocked` でないもの）があるかを確認する。

さらに告示の時期に入ったら、切替前に次の期間について予告する。
4月になってから「料率が無い」と気づくと、その時点で計算できない状態が既に起きているため。

| 対象 | 告示 | 予告が出る時期 | 切替 |
|---|---|---|---|
| 社会保険料率（協会けんぽ・年金機構） | 3月頃 | 3月 | 4月1日 |
| 所得税系（基礎控除・給与所得控除） | 12月に大綱 | 12月 | 1月1日 |

**層3：公開ゲート**

`--gate` オプションで、`approved` でないレコードが1件でもあれば異常終了する。
シミュレータの公開ビルドに組み込み、未承認の値が本番に出ないようにする（§48）。

### 6-3. 年間の流れ

| 時期 | 起きること | システムの動き | 人の作業 |
|---|---|---|---|
| 12月 | 税制改正の大綱 | `check-tax-reform` が新項目を検知 | 影響マスターに `announced` で仮登録 |
| 12月 | — | 鮮度チェックが翌暦年の未登録を予告 | — |
| 3月 | 改正法成立 / 協会けんぽ料率告示 | 鮮度チェックが翌年度の未登録を予告 | 新年度レコードを入力し二者確認 |
| 4月 | 社会保険の新年度 | 対象期間が切り替わる | `approved` へ昇格 |
| 毎月1日 | タックスアンサー更新 | `crawl-nta-sources` がhashを更新 | — |
| 毎月8日 | — | 鮮度チェックが出典変更を通知 | 変更が税率に及ぶか確認 |

### 6-4. 実装

```
masters/
  sources/source-registry.json        出典台帳（何を・いつ・どこで確認するか）
  scripts/check-master-freshness.js   鮮度チェッカー
  ci/check-master-freshness.yml       GitHub Actions（hp-vlog へ配置する）
```

使い方:

```bash
node scripts/check-master-freshness.js                    # 現状の確認
node scripts/check-master-freshness.js --as-of 2027-03-10 # 告示時期の動作確認
node scripts/check-master-freshness.js --gate             # 公開前ゲート
node scripts/check-master-freshness.js --json             # 機械可読出力
```

検知される項目:

| 種別 | 意味 | 対応 |
|---|---|---|
| 出典が更新された | `source_hash` が現在の `html_hash` と不一致 | 原文を読み、影響があれば新レコード追加。無ければ `source_hash` のみ更新 |
| 対象期間のレコード無し | 当年/当年度を覆う有効レコードが無い | 新年度分を入力 |
| 次の期間が未登録 | 告示時期に入ったが次期分が無い | 切替までに入力 |
| 出典が見つからない | ページが削除・移転 | 台帳のURLを修正 |
| 台帳に無い出典 | `source_document_id` が未登録 | 台帳に追加（しないと変更を検知できない） |
| `source_hash` 未記録 | 出典の変更を検知できない状態 | 出典を確認してhashを記録 |

### 6-5. 出典台帳の設計上の注意

`source_document_id` に年度を含めない（`KYOKAI-KENPO-R7` ではなく `KYOKAI-KENPO-HEALTH`）。
出典は同じページであり、年度は `effective_from` が持つ情報のため。
年度入りのIDにすると、毎年台帳を増やすことになり、監視対象から漏れる。

ファイル冒頭の `_extraction_source.html_hash` は、そのファイルが主に写した出典のもの。
別の出典を引くレコードに流用してはいけない。他所のハッシュを自分の出典として記録することになり、
その出典が変わっても気づけなくなる（チェッカーは `taxanswer_id` が一致する場合のみ控えとして使う）。

## 7. レビュー指摘の修正（2026-08-24）

### 7-1. value_key の導入

年度に依存しない意味キー `value_key` を全レコードに付けた。

導入前は、エンジンが値を引くには `IHT-H27-INSURANCE-EXEMPT` のような年度入り `record_id` を
コードに直書きするしかなく、翌年 `IHT-R9-...` になればコード修正が必要だった。
これでは §3-1 の「税率をコードへ直接書かない」が守れない。

```
record_id   BD-R8-TIER-01              世代を含む。人が特定するための番号
value_key   basic_deduction_table      年度非依存。エンジンはこれと適用日で引く
```

段階表は全行が同じ `value_key` を共有し、行の区別は上下限と `calculation_order` が担う。

### 7-2. applicability_conditions の導入

同じ `value_key`・同じ期間・同じ段階のレコードが複数ある場合に、
どちらを使うかを機械可読に書く欄。

中小法人の軽減税率は通常15%だが、所得10億円超の事業年度は17%になる。
導入前はこの条件が `_condition` という注記にしか無く、エンジンは2件のうちどちらを
使うか決められなかった。検証器が同種の重なりを10件検出し、うち5件が実際の欠陥だった。

### 7-3. 別表第五の取得（給与収入660万円未満）

所得税法28条4項により、給与収入660万円未満は給与所得控除の算式表を使ってはならず、
**別表第五**で給与所得を求める。法人成り・役員報酬シミュレータの主対象がこの層なので、
算式で代用すると常時ずれた結果になる（収入5,990,000円で1,600円、最大3,199円）。

e-Gov 法令API（所得税法 340AC0000000033）から別表第五を取得し、次を確認した。

| 区間 | 扱い |
|---|---|
| 〜650,999円 | 給与所得 0（算式なら999円になる） |
| 651,000〜1,899,999円 | 収入 − 650,000円（1円単位） |
| 1,900,000〜6,599,999円 | **4,000円刻みの帯表**（1,175帯） |
| 6,600,000〜8,499,999円 | 収入 × 90% − 1,100,000円 |
| 8,500,000円〜 | 収入 − 1,950,000円 |

帯表1,175行をそのまま持つ代わりに、「収入を4,000円単位に切り捨ててから給与所得控除の
算式を適用する」という規則で持つ。**1,175帯すべてで原文と一致することを検証済み**。

規則は原文からの導出なので、原文の全帯を `data/tax-simulator/masters/fixtures/appendix5-r7-golden.json` に
残し、規則が表を再現し続けることを `test-appendix5-rule.js` で担保する。
改正で規則が崩れればテストが落ちる。

### 7-4. 仕様書 §3-1 フィールドの充足

`tax_year`・`calculation_order`・`rounding_rule_id`・`promulgated_at`・`verified_at`・
`verified_by`・`applies_to_period_start_*`・`applies_to_transaction_*` を全レコードに付けた。

ただし **項目を null で埋めれば充足率は100%になるが、それは中身が決まったことを意味しない**。
「考えた上で該当なし」と「まだ決めていない」を区別するため、次の扱いにしている。

- 丸めが起きないレコードには端数規則 `R-NONE` を明示的に置く（56件）
- 丸め位置の判断に税務の知識が要るレコードは `null` のまま残し、検証器が名指しで警告する

現在 **36件が端数処理未決定**（法人税・事業税・住民税所得割・社会保険の率適用段階）。
これらは率を掛けて金額を出すため、どの段階で何円未満を切り捨てるかの判断が要る。
推測で規則を当てず、税理士承認の工程で決める。

### 7-5. 出典URLの確認状況

台帳30件のうち、実体を確認できたのはタックスアンサー13件と e-Gov 1件。
残り16件は記憶で書いたもので、通知の「確認先」として機能しない可能性がある。
`url_verified: false` を立てて可視化した。
うち1件（地方法人税）は実際に誤り（グループ通算制度のページを指していた）で修正済み。

### 7-6. 検証器の追加

`scripts/validate-masters.js` を追加した。鮮度チェックが「今の法令に追いついているか」を
見るのに対し、こちらは「データとして壊れていないか」を見る。

| 検査 | 内容 |
|---|---|
| 型 | Money / Rate が整数文字列か（浮動小数を混ぜていないか） |
| 段階の連続性 | 隙間・重なり。端数規則の刻み幅を踏まえて判定する |
| 適用期間の重なり | 同じ value_key・同じ段階で期間が重なっていないか |
| 参照 | rounding_rule_id が端数規則表に存在するか、record_id の重複 |
| 充足率 | 仕様書 §3-1 のフィールドが埋まっているか |
| 中身 | 端数処理の未決定、出典内の位置の未記載 |

段階の連続性の判定では、課税所得が1,000円未満切捨てであることを考慮する。
所得税の速算表は 1,949,000 の次が 1,950,000 で、1円刻みで見ると隙間に見えるが、
その間の値は存在しない。

## 8. 社会保険マスターの整備（2026-08-24）

### 8-1. 標準報酬月額の等級表

e-Gov 法令APIから取得。健保50等級・厚年32等級、計82レコード。

**重要な落とし穴：法令原文だけでは現行の等級表にならない。**

厚年20条2項は「政令で、当該最高等級の上に更に等級を加える標準報酬月額の等級区分の改定を
行うことができる」と定めており、**改定しても法本文の表は書き換わらない**。
そのため e-Gov の厚生年金保険法を読むと第31級（620,000円）までの31等級に見える。

現行の32等級は **令和2年政令第246号** 第1条の読替えによる。

| | 法本文（20条1項） | 政令246号による読替え後 |
|---|---|---|
| 第31級 | 620,000円 / 605,000円以上 | 620,000円 / 605,000円以上**635,000円未満** |
| 第32級 | （無し） | **650,000円 / 635,000円以上** |

同じ政令の第2条が、厚年の標準賞与額の上限150万円も定めている。
厚年24条の4第1項は「等級区分の改定が行われたときは政令で定める額」としているため、
等級改定のたびにこの政令を確認する必要がある。

健保側にも40条2項に同じ改定規定があるが、現在は該当する政令が存在しない

### 8-3. 適用期間の起点が3つある

### 8-4. 自動読取りで取り込んだ値の扱い

都道府県別の健康保険料率47件×2年度は、協会けんぽのページの自動読取りで取り込んだ。

- 健保法160条1項の法定範囲（3%〜13%）に収まるか
- 47都道府県が過不足なく揃っているか
- 常識的な幅（8%〜12%）から外れた値が無いか（桁の取り違えを弾く）

二者確認では協会けんぽの公式PDF（都道府県別保険料額表）と突合すること。

### 9-2. 出典URLを全件確認した

台帳37件すべてを実際に開いて確認した。**記憶で書いていた17件のうち11件が実際に誤り**だった
（404・403・別ページ）。

| 厚年保険料率・標準賞与額の上限（年金機構／協会けんぽ） | 法令を出典にしたため台帳から削除 |

`scripts/verify-source-urls.js` を追加した。到達性に加えて、
ページに期待する語が含まれるかも見る（別ページに転送されていても気づける）。

日本年金機構だけは node の fetch からの接続を切られる（UAを変えてもECONNRESET）。

人が開いて確認する扱いにした。失敗し続けて通知が無視されるのを避けるため。

### 9-3. 協会けんぽ料率は PDF を読む必要がない

料率一覧はHTMLの表なので、モデルに読ませずに解析できる。
`scripts/fetch-kenpo-rates.js` が表を直接パースし、全94件がマスターと
一致することを確認した。保険料額表のPDFはCIDフォントで機械抽出できないが、
料率そのものはPDFを見なくても取れる。

毎年3月頃に翌年度分が公表される。鮮度チェックが3月に予告を出すので、
それを受けて `--year r09` のように指定して突合し、`--write` で反映する
（値が変われば承認状態は unverified に戻る）。

### 9-4. 相続税の税額控除を追加した

| 控除 | 内容 | 出典 |
|---|---|---|
| 未成年者控除 | 10万円 × 満18歳までの年数 | No.4164 |
| 障害者控除 | 10万円（特別障害者20万円）× 満85歳までの年数 | No.4167 |

## 10. 検証・承認・R8対応（2026-08-24）

### 10-1. 地方税を法令で検証して誤りを1件発見

住民税・法人住民税・事業税を、これまで条文を読まずに登録していた。
地方税法の原文で確認したところ、**政令指定都市の内訳が誤っていた**。

| | 非指定都市 | 政令指定都市 |
|---|---|---|
| 所得割 | 市6% ＋ 県4% | **市8% ＋ 県2%** |
| 調整控除 | 市3% ＋ 県2% | **市4% ＋ 県1%** |

合計（所得割10%・調整控除5%）は同じなので総額は変わらないが、
市民税・県民税を分けて表示するなら区別が要る。
`applicability_conditions` で `is_designated_city` により選び分ける形にした。

法人住民税6%/1%・事業税3.5/5.3/7%・地方法人税10.3%・特別法人事業税37%・
森林環境税1,000円は、いずれも条文と一致していた。

### 10-2. 所得税の0〜999円は問題ではなかった

課税標準は1,000円未満切捨て（通法118条1項）なので、取りうる値は0か1,000以上しかない。
所得税の速算表が1,000円から始まるのはそのためで、隙間ではない
（0〜999は切り捨てられて0になり、税額も0）。

検証器が「段階表が1000から始まる」と警告していたのは誤検知だった。
端数規則の刻み幅を見て、最下段の下限が刻み幅と等しければ警告しないよう直した。

### 10-3. R8の値を大綱から取得した

**基礎控除 R8・R9**（令和8年度税制改正の大綱）

| 合計所得金額 | 控除額 | 内訳 |
|---|---|---|
| 489万円以下 | **104万円** | 62万 ＋ 特例加算42万 |
| 489万円超655万円以下 | **67万円** | 62万 ＋ 特例加算5万 |
| 655万円超2,350万円以下 | **62万円** | 58万→62万に引上げ |
| 2,350万円超2,400万円以下 | 48万円 | 改正なし |
| 2,400万円超2,450万円以下 | 32万円 | 改正なし |
| 2,450万円超2,500万円以下 | 16万円 | 改正なし |
| 2,500万円超 | 0円 | 適用なし |

**タックスアンサー No.1199 の令和8年分列（95万／88万／68万／63万／58万）は
令和7年度改正時点の内容で、令和8年度改正が上書きしている。**
No.1199 の法令基準日は令和7年4月1日なので未反映。これだけを見て登録してはいけない。
blocked にしていたおかげで誤った値が入らずに済んだ。

**給与所得控除 R8**: 最低保障額 69万円（恒久）＋ R8・R9の特例5万円 ＝ **74万円**。

ただし大綱には段階ごとの表が無い。第1段階の上限2,200,000円は、

### 10-4. 承認（294件）

出典と一致を確認したレコードを承認済みにした（`verified_by: 毛利順活税理士事務所`）。

`scripts/approve-records.js` が対象を選ぶ。次のものは自動的に外れる。

- `blocked`（確認待ち）
- `_boundary_derived: true`（出典に書かれていない値を計算で埋めたもの）
- `source_locator` が未記載のもの

**施行前でも承認しうる。** 「値が確認できたか」（`data_review_status`）と
「適用中か」（`legal_status`）は別の軸で、施行前でも出典に金額が明記されていれば
値としては確認できる。計算エンジンは `legal_status` を見て、
施行前の値を使ったことを結果に表示する。

残り7件: インボイス経過措置5件（R8改正の控除割合が未確認）、

### 10-5. 公開ゲートは対象を絞る必要がある

`--gate` は現在マスター全体を見るので、インボイス5件が未確認なだけで
すべてのシミュレータが止まる。

本来はシミュレータごとに、使う `value_key` の集合だけを見て判定すべき。
法人成りシミュレータが相続税マスターの未承認で止まるのはおかしい。
計算エンジンの実装時に、シミュレータ→value_key の依存表を作って
ゲートをその範囲に絞る。

## 11. 概算値の扱いとインボイス経過措置（2026-08-24）

### 11-1. 導出値を概算として使えるようにした

給与所得控除R8の段階の境界は大綱に書かれておらず、導出した値だった。
出さないより概算でも出したほうが利用者の役に立つため、使える形にした。

ただし確定値と区別できないまま公開されては困るので、承認とは別の軸を持たせた。

| フィールド | 意味 |
|---|---|
| `value_certainty` | `confirmed_from_source`（出典に書かれている）/ `derived`（導出した） |
| `requires_result_warning` | 計算結果に注記を出す必要があるか |
| `_derivation` | どう導いたかの説明 |
| `_warning_text` | 結果に添える文言 |
| `_affected_range` | 導出が結果に影響する範囲 |

`data_review_status`（審査が終わったか）と `value_certainty`（値の性質）は別物。
承認済みでも導出値なら注記が要る。

承認スクリプトは、`value_certainty: "derived"` のレコードについて
`requires_result_warning` と `_derivation` と `_warning_text` が揃っていることを
確認してから承認する。表示の担保が無いまま承認されるのを防ぐため。

**計算エンジンへの要件**: 導出値を含む計算では `resultStatus` を `partial` とし、
`_warning_text` を結果に添える。

給与所得控除R8の場合、影響するのは**給与収入190万円超220万円以下**の範囲だけで、
最大9万円（控除額）ずれうる。この範囲外では境界の取り方によらず同じ結果になる。

### 11-2. インボイス経過措置を大綱で確定

令和8年度税制改正の大綱 四 消費課税 2（2）で確認した。

| 期間 | 控除割合 |
|---|---|
| 〜令和8年9月30日 | 80% |
| 令和8年10月1日〜令和10年9月30日 | **70%** |
| 令和10年10月1日〜令和12年9月30日 | **50%** |
| 令和12年10月1日〜令和13年9月30日 | **30%** |
| 令和13年10月1日〜 | 適用なし |

改正前は令和8年10月1日から50%になる予定だったが、70%に引き上げたうえで期間を延長し、
段階を3つに増やしている。

**相手先ごとの上限**: 「一の適格請求書発行事業者以外の者からの課税仕入れの額の合計額が
その年又はその事業年度で1億円（**現行：10億円**）を超える場合には、その超えた部分の
課税仕入れについて、本経過措置の適用を認めない」。

「課税仕入れの額」が税込か税抜かは大綱の文言だけでは確定できないため、
`_needs_confirmation` に残した。改正法の条文で確認する。

### 11-3. approved は対外的な保証ではない

`data_review_status: "approved"` と `verified_by` は、**事務所の確認工程を通った
ことの内部記録**であって、計算結果に対する対外的な保証ではない。

シミュレータの結果には、税務記事と同じ趣旨の免責事項を表示する。

> 本記事は情報提供を目的として作成しており、個別の税務アドバイスではありません。
> 実際の税務判断・手続きについては、税理士等の専門家にご相談ください。
> 税制は改正される場合があり、記事の内容が最新状況と異なることがあります。
> 個別事情によって結論が異なる場合がありますので、必ずご自身の状況に合わせて
> ご確認ください。
>
> — `templates/blog-post.html` の `.blog-disclaimer`

出典を確認して丁寧に値を作ることと、結果を保証しないことは両立する。記事と同じ構造。

**承認済みであることを理由に免責を省いてはいけない。
免責があることを理由に確認工程を省いてもいけない。**
仕様書にも「免責文だけで信頼性を代替しない。誤り報告窓口、訂正履歴、
影響を受けた計算バージョン、再計算案内を用意する」とある。

この区別を書き残すのは、`approved` を「事務所が個々の値を保証した」と
読み違える可能性があるため。実際に読み違えが起きたので明記しておく。

### 11-4. 承認状況

**301件すべて承認済み。未承認0件・確認待ち0件で、公開ゲートを通過する。**

ただし大綱を出典とするレコード（`legal_status: enacted`）は条文ではないため、
改正法の公布・施行後に条文で確認し直す必要がある。
