### 1. High: 中身を読めないページも「項目の無いページ」になり、取り込みが進む
`scripts/lib/tsutatsu-parser.js:203-210`

「項目の無いページ」かどうかを、「番号が見つからなかった」ことだけで決めています。さらに、項目の無いページの数には上限がありません。修正前は項目 0 件のページで止まっていましたが、今は素通りします。法人税の URL で試した結果、次はすべて「項目の無いページ」になりました。
- 中身が空の正常応答（`''`）
- メンテナンス中のページ（`<title>メンテナンス中</title>…`）、途中で切れた HTML
- 番号の書き方がまた変わったページ: `<span class="fw-bold">1－3－2</span>`、`<span style="font-weight:bold">`、`<em>`、`<p>` の代わりの `<div>`

最後の例は、今回の分類 A（`span.bold`）と同じ種類の変化です。次に起きたときは止まらず、そのページの条が黙って抜けます。

- **何が起きるか**: たとえば法人税（257 ページ）で 30 ページがメンテナンス中の画面で返ると、条の減ったカタログで既存のものが上書きされます。「条が減っていないか」はマージ後の手動確認だけです。
- **試験の書き換え**: `test-fact-review-fixes-3.js:180` は、もとは「前文だけで項目のないページなら止まる」ことを確かめる試験でした。今回、番号付きの空のページに書き換えられ、この安全側の試験は無くなっています。
- **直し方の案**（(c) が一番効きます）:
  - (a) 「項目の無いページ」とするには、裏付けを求める。URL が附則・別紙・前文であること、または国税庁の本文ページの形（タイトルに「｜国税庁」、`<h1>` か本文の印、ある程度の本文の長さ）があること。どちらも無ければ読み落としにする。
  - (b) リンク切れと同じく、項目の無いページにも上限を設ける。前回のカタログの `non_provision_pages` に無い URL が増えたら止める、など。

### 2. High: 番号らしいかどうかを今の番号の形で判定しているため、知らない形の番号を見逃す
`scripts/lib/tsutatsu-parser.js:203-208`

`01-fixes.md` の R3 は「中身が数字で始まる」太字を番号らしい書式としています。実装は代わりに今の番号の形の判定（`looksLikeProvisionNo` など）を使っています。番号の形が合えばふつうは読めるので、この確認は読み落としの代表例である「知らない形の番号」を拾えません（2026-08-21 のリース取引 12の5-1-1 と同じ種類です）。試すと、`<strong>12の5の2-1-1</strong>`（法人税）や `<strong>37-13の2の2</strong>`（所得税）だけのページは「項目の無いページ」になりました。

**「(共)」の 3 ページはこれにあたり、実際の通達の項目が 10 件抜けます**:

| ページ | 見出し | 番号 |
|---|---|---|
| `01_42_05_1` | 第42条の6～第47条《共通事項》関係 | 42の6～47(共)-1〜5・-3の2（6 件） |
| `02_55` | 第55条～第57条の8《共通事項》関係 | 55～57の8(共)-1・-2 |
| `10_64` | 第64条～第66条《共通事項》関係 | 64～66(共)-1・-2 |

どれも本文があります。記録される理由は「段落の先頭に番号らしい書式がありません」ですが、事実と違います。実装者の「数字で始まる、の条件に従った」という説明も当たりません。中身は 42・55・64 と数字で始まっているので、R3 のとおりなら読み落としで、措置法（法人税編）は止めるべきです。

- **指示書の食い違い**: README 36 行は「中身が通達番号の形」と書いており、`expected.json` もこの 3 ページを `provisions_or_non_provision` にしています。実装はこちらに合っているので、どちらに寄せるかは指示書を書いた側が決める必要があります。
- **直し方の案**: 番号らしい書式を「段落の先頭の太字が数字で始まる。ただし財産評価以外で数字だけ（`^\d+$`、附則の「1」「2」）は除く」にする。66 ページに当てはめると、変わるのはこの 3 ページだけです（所得税 40/01 の附則の「1」〜「5」は、項目の無いページのまま）。
- **そのあとの選択**: `expected.json` を「読み落とし」に直して措置法（法人税編）を止めるか、「(共)」を読めるようにするか（たとえば `normalizeProvisionNo` で「(共)」を「共」に寄せる）。後者は番号の形の判定に当たり、照合で引く側の番号にも影響するので、判断が要ります。
- 【推測】「(共)」の項目が普通の項目と同じページに並ぶ場合、`parseExtendedPage` は直前の項目の本文に混ぜてしまいます。これは今回の差分より前からの動きで、実際にそういうページがあるかは確かめていません。
