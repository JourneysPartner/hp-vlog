# 題名差し替えの試験 test-title-refresh.js を、その後の手直しを許す形に作り直す（title-refresh-test）

2026-11-11 利用者決定（案 2「作り直す」）。

## 何が起きているか

`scripts/lib/__tests__/test-title-refresh.js` は、2026-09 の題名・説明文の差し替え（crawl-queue 09、`docs/codex-tasks/crawl-queue/09-title-refresh.md`）で対象にした記事 10 本について、次を固定している。

- 題名・説明文が指定の値であること
- 本文と、題名・説明文以外の frontmatter が、差し替えのときから 1 字も変わっていないこと（本文を含む指紋 `fullHash`）
- 鮮度更新（`updated_at` と `reviewed_at` が同じで 2026-09-28 以降）の記事だけは、本文と更新日の変更を許す（指紋 `freshHash`）

差し替えより後の正しい変更で、この試験は 3 回落ちている。

| 日 | 変更 | 試験の扱い |
|---|---|---|
| 2026-10-08 | 鮮度更新の更新案（#663）でサブスクの記事の本文と更新日が変わった | draft-supply 03 で鮮度更新を許す形にした |
| 2026-11-06 | 毛利承認の手作業の PR（#751 など）で題名・説明文・本文を変えた | 同じ PR で試験の期待値を手で直した |
| 2026-11-10 | 承認画面の手直し PR（#762）で塗装工の消耗品の記事の本文を 1 行変えた（更新日・確認日は変えない） | 直していない → main の CI（Check Tax Simulator Masters）が赤のまま |

本文と題名・説明文の変更は、鮮度更新の承認（`/admin/freshness`）と、手直し PR の承認（#759）でそれぞれ人が確かめてから入る。この試験が差し替えのときの本文と題名を固定し続ける理由はもう無く、正しい変更のたびに CI を赤にしている。

## 方針

- **本文と題名・説明文の固定をやめる。** 差し替えそのものの確かめ（本文を変えていない）は、差し替えの PR の CI で済んでいる。
- **公開した後に変わってはいけない 11 項目だけを、名前を決めて固定し続ける**（固定の項目）: `slug`・`category`・`article_type`・`customer_segment`・`source_url`・`source_title`・`source_provenance`・`created_at`・`publish_at`・`published_at`・`pr_number`。
  - 点数（`*_score`）・`recommendation`・`review_warning`・`related_*`・`search_intent` などは、あとの照合・内部リンクの更新・鮮度更新で正しく変わりうるので固定しない。項目が足されても落とさない（今の指紋は、項目を 1 つ足しただけでも落ちる）。
  - 値は記事ごとにそのまま書く（指紋にしない）。落ちたときに、どの記事のどの項目が変わったかを出すため。
  - 値は今の記事から写してよい。2026-11-11 に、10 本とも「題名・説明文・更新日・確認日を除いた frontmatter」の指紋が差し替えのときの値（今の `freshHash`）と一致することを確かめた＝今の値は差し替えのときの値と同じ。写す前に、試験の中でもこの一致をもう一度確かめる（下の Q2）。
- 更新日は「差し替えのときより前に戻っていない」だけを確かめる（手直しで更新日を進めても落ちない）。
- 対象 10 本が公開記事として 1 本ずつあること、説明文が 120 字以内であることは今のまま確かめる。

### 弱くなる点（記録）

- 自動の仕組みの不具合で、この 10 本の題名・説明文や本文が書き換わっても、この試験では気づかない。題名の形は `test-title-lint.js`・`test-seo-lint.js`、鮮度更新と手直しはそれぞれの試験と人の承認で見ている。
- 鮮度更新かどうかの判定（`isFreshnessUpdated`）と、その試験 4 本（「差し替えより前の確認日は鮮度更新扱いしない」など）は、使わなくなるので消える。
- 固定の 11 項目のほかの frontmatter（点数・推奨・関連記事・検索の意図など）が変わっても、この試験では気づかない（今は、手直しや鮮度更新でも変わっていないことを指紋で見ていた）。

## 要件

- **Q1** 頭の注記を、今の目的（ずっと変わってはいけない項目の固定）と、上の表の経緯の短い説明に書き換える。
- **Q2** `EXPECTED` の各記事を `{ file, slug, updated_at, pinned: { 固定の 11 項目の値 } }` にする。`pinned` の値は今の記事から写す。写す前に、今の `stableHash(parsed, file, true)` が今の `freshHash` と一致することを 10 本とも確かめ、一致しない記事があれば写さずに報告して止まる（この確かめは作業の中でだけ行い、試験のファイルには `freshHash`・`fullHash`・`title`・`summary` を残さない）。記事に無い項目は `pinned` に入れず、「無いこと」を確かめる。題名・説明文の差し替えの経緯の注記（「2026-11-06 毛利承認で…」）は、1 行の履歴として残してよい。
- **Q3** 「1. 対象」: 公開記事が 1 本だけ（`review_status === 'published'`）、説明文が 120 字以内、更新日が `EXPECTED.updated_at` より前でない（`Date.parse` で比べる。読めない日付は落とす）、を確かめる。題名・説明文が指定の値かの確かめは消す。
- **Q4** 「2. 公開の後に変わってはいけない項目」: 記事ごと・項目ごとに、今の値が `pinned` の値と等しい（`pinned` に無い項目は記事にも無い）ことを確かめる。確かめの名前に記事と項目を入れる（例: `<slug>: source_url は差し替えのときから不変`）。本文・題名・説明文・ほかの項目は見ない。
- **Q5** 「3. 偽データで変更の検出を確かめる」を、新しい決まりに合わせて作り直す。実際の記事に頼らず、偽の記事 1 本（今の `fixture-ordinary.md` の形に、固定の 11 項目を全部持たせたもの）で次を確かめる。
  - 本文を変えても通る／題名・説明文を変えても通る／更新日・確認日を進めても通る／固定でない項目（例: `customer_fit_score`、`related_slug`）を変えても、足しても通る
  - 固定の 11 項目のどれを変えても落ちる（11 項目それぞれ）／固定の項目を消しても落ちる／`pinned` に無い固定の項目を足しても落ちる
  - 更新日を基準より前に戻すと落ちる／読めない更新日は落ちる
- **Q6** 使わなくなった `isFreshnessUpdated`・`chooseOrdinaryArticle` と、それだけを確かめていた試験は消す。消した確かめの名前を報告に全部書く。
- **Q7** 結果の出し方（`PASS: n / FAIL: m`、失敗があれば終了コード 1）は今のまま。
