### 2. 修正で新しく入った問題

**Low：ログインのボタンを 2 回押すと「しばらくしてからお試しください」（429）が出る**（F2 を直した後に起きる）
- **場所：** `review-auth.js:235`・`:199-201`、フォームは `:179`
- **何が起きるか：** 送信を 2 回すると、2 回目の要求は書き込みの競合で 429 になります。2 回の間隔が、Blobs への 4 回の読み書きの間に収まる場合です。
  - ブラウザは後の応答を表示するので、正しいパスワードでも「しばらくしてから」と出ます。
  - 1 回目の成功の Cookie が残るかどうかは**推測**で、確かめていません。数は 2 回分増えます。
- **直し方：** ログイン画面の nonce 付きスクリプトで、送信のときにボタンを押せなくする。競合のときの文言を「もう一度お試しください」に分ける。

### 3. 特に見てほしい点

**F1：Origin が付くか → 付きます（仕様で確認、ブラウザでは未確認）**
- Fetch 標準では、GET・HEAD 以外の要求で `same-origin` のとき、同じサイトへの要求には本当の Origin を付けます。
- ログインのフォームの POST も、画面からの `fetch()`（3 つの処理・確認・ログアウト）も同じ扱いです。
- 妨げになるものもありません。
  - 画面に `<meta name="referrer">` はありません。
  - フォームに `rel="noreferrer"` もありません。
  - `netlify.toml` の `Referrer-Policy` は `/tools/*` だけにかかります。
- **前回の訂正：** 前回「`fetch()` は mode が cors なので影響を受けない」と書いたのは、仕様の上では誤りでした。同じサイトへの `fetch()` も同じ分岐を通るので、`no-referrer` の下では `Origin: null` になりえました。今回の変更で、こちらも直っています。

**F2：順番と戻り値の扱い**
- **順番：** 問題ありません。止められているときは書かずに 429 を返します（`:226`）。照合（`:242`）に進むのは、2 つの書き込みがどちらも `modified === true` のときだけです。
- **`modified` の扱い：** コードは正しいです。`false` なら 429（`:235`）、`true` 以外なら 503（`:236`、`:251-253`）を返します。
- **通してしまう経路 その 1（主因）：** ライブラリが条件を送りません。いずれも 10.7.9 の `dist/main.cjs` で、本体の checkout の node_modules を読んで確かめました。
  - `setJSON` は `makeRequest({ ...conditions, ... })` と、条件を展開して渡しています（`:635-636`）。
  - 一方、`makeRequest` は `conditions = {}` という名前でしか受け取りません（`:314-316`）。このため `if-match`・`if-none-match: *` が付きません（`:340-343`）。
  - その結果、どの書き込みも通り、`:650` で必ず `{ modified: true }` が返ります。
  - `set()` のほうは `conditions` をそのまま渡しているので、条件が効きます（`:596-597`）。
  - コードを読んでの確認で、実際の API に対しては動かしていません。
- **通してしまう経路 その 2：** 条件を付けた書き込みでは、412 以外のどの状態も `modified: true` として返ります（`:610`・`:650`）。
  - 書き込みが 400・401・403・404 などで失敗しても「書けた」扱いになり、照合に進みます。
  - 5xx と 429 は 5 秒待って最大 5 回やり直すので（`:155-175`）、関数の時間切れで止まり、照合には進みません。
  - 前のコードも書く前に照合していたので、前より悪くはなっていません。ただし、「書けてから照合する」という今回の設計は守られていません。
- **常に止める経路：** Blobs の読み込みの応答に ETag が無いと、毎回 503 になります（`:196`）。これは本番の Blobs の実確認の範囲なので、指摘にはしません。
- **直し方：**
  - `store.set(key, JSON.stringify(record), condition)` に替える（読む側の `type: 'json'` はそのままで読めます）。
  - `getStore({ ..., fetch })` に、書き込みの応答が 200 と 412 以外なら例外を投げる `fetch` を渡す。簡単にするなら、空でない `result.etag` も条件にする（ただしエラーの応答に ETag が付かない前提で、これは**推測**です）。
  - 試験は偽のストアではなく、本物のライブラリに偽の `fetch` を渡して作る。書き込みに `if-match` と `if-none-match: *` が付くこと、書き込みの 403・500 で照合せずに 503 になることを確かめます。
- **範囲外ですが：** `analytics-store.js:186-187` と `:212-213` も同じ `setJSON` の条件付きの書き込みなので、同じ理由で条件が効いていない見込みです。

**F8：確認が 204 以外なら承認を送らないか → 送りません（`review-page.js:521-527`）**
- 401 なら `requireLogin()` を呼んで止まります。
- 204 以外なら例外を投げます。通信の失敗も同じく `catch` に入り、エラーを出してボタンを戻します。どちらの場合も承認の要求（`:533`）には進みません。
