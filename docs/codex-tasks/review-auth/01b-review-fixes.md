## F1（High）ログインのフォームが必ず 403

- 原因: 2 つの画面の `Referrer-Policy: no-referrer`。Fetch 標準では、この方針で POST のフォームを送ると、ブラウザは `Origin: null` を送り、`Referer` も送らない。`validOrigin` が 403 を返す。試験は Origin を手で入れているので見つからなかった。
- 直し方:
  - レビュー画面とログイン画面の `Referrer-Policy` を `same-origin` にする（同じサイトへの要求には本当の Origin が付き、外のサイトへは何も送らない）。
  - `/review-login` が返す 403・405・429・503 は、JSON ではなくログイン画面の HTML で返す（ステータスは保ち、利用者に分かる文言を出す。理由の細部は出さない）。
- 試験: 2 つの画面の `Referrer-Policy` が `same-origin`（`no-referrer` でない）。ログイン画面のフォームの送り先が同じサイトの `/review-login`。`/review-login` の 403・429・503 の応答が HTML のログイン画面。

## F2（Medium）同時の要求で上限が効かない

- 原因: 「読む → パスワードを照合 → 数を書く」の順で、書く前に別の要求が同じ数を読める。偽のストアで 200 件同時に送ると、200 件とも照合まで進み、数は 1 だった。
- 直し方:
  - **照合の前に 1 回分を数える。** `getWithMetadata` で記録と etag を取り、`setJSON(key, 次の記録, { onlyIfMatch: etag })`（記録が無いときは `{ onlyIfNew: true }`）で書く。IP ごとと全体の両方。
  - 条件付きの書き込みが通らなかった（`modified: false`）要求は、**照合せずに** 429（「しばらくしてからお試しください」のログイン画面）を返す。やり直しはしない。
  - 書き込みが通ってから照合する。合えば、その IP の記録を消して Cookie を出す（今どおり、消せなければ 503）。合わなければ 401（数は既に増えている）。
  - 全体の数は「試行の数（成功も含む）」になってよい（毛利さんのログインは 1 日に数回）。
  - 上限・停止時間・通知の条件（同じ IP 15 分 5 回、全体 1 時間 30 回）は変えない。
  - 導入済みの `@netlify/blobs` の型（`node_modules/@netlify/blobs/dist/main.d.ts`）で、`onlyIfMatch`・`onlyIfNew`・`getWithMetadata` の形と、`setJSON` の戻り値（`modified`）を確かめてから使う。
- 試験: 偽のストアを etag と条件付きの書き込みに対応させる（読み書きに遅れを入れる）。同じ IP から誤ったパスワードを 200 件同時 → パスワードの照合が呼ばれた回数が 5 以下、残りは 429。全体で 200 件同時（IP をばらばら）→ 照合は 30 以下。条件付きの書き込みが通らない要求で照合が呼ばれない。

## F3（Medium）閉じていないタグ

- 原因: `review-html.js` の除去は、タグの開け閉めを揃えない。`<a href="https://evil.example/">続き` だけの本文で、本文より後ろ（照合の詳細・コメント欄）がそのリンクの中に入りうる。余分な `</div>` で本文の枠を抜けることもできる。
- 直し方:
  - 開いているタグを積み上げて覚える。中身の無い要素（`br`・`hr`・`img`）は積まない。
  - 閉じタグは、開いているものの中にあれば、そこまでを全部閉じる。開いていない閉じタグは捨てる。
  - 本文の最後で、開いたままのタグを全部閉じる。
  - `p` の中の `div` などの入れ子の厳密な規則までは要らない（本文の外に出ない・後ろに広がらないことが目的）。
  - 本文のリンク（`a`）には `target="_blank" rel="noopener noreferrer"` を付ける（`#` で始まる同じページ内のリンクは除く）。
- 試験: `<a href="https://evil.example/">続き` だけの本文 → 除去後の HTML で `<a` と `</a>` の数が同じで、レビュー画面の本文のカードの閉じタグより前で閉じる。余分な `</div></div><script>…` → 本文のカードの外に何も出ない。`<table><tr><td>` だけ → 全部閉じる。普通の記事（`fixtures` の下書き）は見た目が変わらない（`a` の属性だけ増える）。

## F4（Low）IP の偽装

- `x-forwarded-for` は使わない。IP は `x-nf-client-connection-ip` だけから取る。無い・重複して読めないときは、固定の 1 つの区分（`unknown`）にまとめる。
- 試験: `x-forwarded-for` を毎回変えても、同じ区分として数えられる。

## F5（Low）IP のハッシュ

- IP の鍵を、元の秘密（`REVIEW_SESSION_SECRET` か `GH_APP_PRIVATE_KEY`）から HKDF で作った**別用途の鍵**（info `hp-vlog review ip v1`、パスワードは混ぜない）の HMAC にする。パスワードを変えても失敗回数は残る。
- ログに出す 8 文字も、この HMAC から取る。
- 試験: 同じ IP は同じ鍵、別の秘密では別の鍵。パスワードを変えても同じ鍵。

## F6（Low）外部の画像

- 2 つの画面の CSP を `img-src 'self' data:` にする。
- 除去処理で、`img` の `src` が `/` で始まる同じサイトのもの以外（`http:`・`https:` の外部）は、要素ごと落とす（`alt` の文字も出さない）。
- 試験: 外部の画像は残らない、`/images/...` は残る。

## F7（Low）`safeNext`

- 文字列のどこかに `http` があるだけで捨てる確認をやめる。残すもの: 制御文字・`\` の拒否（最大 3 回まで復号して確かめる）、先頭の `//` の拒否、`new URL` で origin が本番かつ道筋が `/review` であること。
- 試験: `ref=draft/http-guide` や、ファイル名に `https` を含む `next` は保たれる。今の拒否の試験（外部・`//`・`\`・改行・`/admin`）は全部そのまま通る。

## F8 承認の前の同期の確認

- 新しい関数 `review-auth-check.js`（POST）: `requireAction` をそのまま使い、通れば 204、通らなければ今と同じ 401・403・503（JSON）。本体の処理は何もしない。
- 画面のスクリプト: 承認のときだけ、承認の要求の前に `/.netlify/functions/review-auth-check` へ同じヘッダ（`Content-Type: application/json`・`X-Review-Token`）・本文 `{}` で POST する。401 なら `requireLogin()`、それ以外で 204 でなければエラーを出してボタンを戻し、**承認の要求を送らない**。
- 承認のバックグラウンド関数の中の確認（`requireAction`）は残す（二重の守り）。
- 試験: 確認の関数の 204・401・403・503。画面のスクリプトが承認の前に確認を呼び、204 以外では承認を送らない（スクリプトの文字列と、偽の `fetch` で動かす）。
