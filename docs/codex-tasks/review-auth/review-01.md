# セキュリティレビュー：レビュー画面と承認・差し戻し・見送りのパスワード認証

**結論：まだマージできません。** High が 1 件あります。このままだと毛利さんはログインできず、レビューの操作が全部止まります。攻撃者が入れる抜け道ではありません。直し方は 1 行です。Medium は 2 件、Low は 4 件です。

スクリプトが動く経路、認証より先に GitHub の処理が走る経路、オープンリダイレクトは見つかりませんでした。

## 指摘

### 1. High：ログインのフォームが必ず 403 になる
**場所：** `netlify/functions/lib/review-auth.js:55`（`Referrer-Policy: no-referrer`）と `:130`（Origin の確認）

- **何が起きるか：** ログイン画面に `Referrer-Policy: no-referrer` が付いています。Fetch 標準では、この状態で POST のフォームを送るとブラウザは `Origin: null` を送り、`Referer` も送りません。`validOrigin` は `'null' !== 'https://mori-zeirishi.net'` で 403 を返します。
  - 結果として、Chatwork のリンク → パスワード入力 → `{"error":"この操作は許可されていません"}` の JSON が出るだけになります。誰もログインできません。
- **確かめたこと：** Fetch 標準の原文（「append a request `Origin` header」）で確認しました。実際のブラウザでの再現はしていません。
  - 画面からの `fetch()` は mode が "cors" なので、普通の Origin が付きます。3 つの処理とログアウトは影響を受けません。
  - 試験は Origin を手で入れているので、この不具合を見つけられません。
- **直し方：** 2 つの画面とも `Referrer-Policy: same-origin` にする。同じサイトへの POST では本当の Origin が付き、外のサイトへは何も送りません。
  - 試験に「ログイン画面の Referrer-Policy が `no-referrer` でない」を足す。
  - あわせて `/review-login` の 403・503・405 も、JSON ではなくログイン画面の HTML で返すと、利用者に分かる表示になります（Low）。

### 2. Medium：同時に送ると失敗回数の上限が効かない
**場所：** `review-auth.js:201`〜`221`

- **何が起きるか：** 処理の順番が「読む → パスワードを照合 → 数を書く」で、書く前に別の要求が同じ数を読めます。
  - 偽のストア（1 回の読み書きに 30ms）で、同じ IP から誤ったパスワードを 200 件同時に送りました。**200 件とも 401 で照合まで進み、IP の数も全体の数も 1** でした。
  - 本番でも、送る数を増やせば「1 時間に 30 回」の何倍も試せます。パスワードが推測しやすいものなら、この差が効きます。
  - 指示書は「厳密な整合までは要らない」としていますが、ここまでの差は想定外のはずです。
- **直し方：** 導入済みの `@netlify/blobs` 10.7.9 は条件付きの書き込みが使えます。
  - `getWithMetadata` で etag を取り、`setJSON(..., { onlyIfMatch: etag })`（記録が無いときは `onlyIfNew: true`）で、**照合の前に** 1 回分を数えます。
  - `modified: false` なら照合せずに 429 か 503 を返します。成功したときに、その IP の記録を消します。
  - 同時の要求で数が増えることを確かめる試験を足します。

### 3. Medium：閉じていない `<a>` がページの残りを外のサイトへのリンクにする
**場所：** `netlify/functions/lib/review-html.js:17`〜`69`

- **何が起きるか：** 除去処理はタグの開け閉めを揃えません。
  - 本文に `<a href="https://evil.example/">続き` とだけ書くと、`marked` も除去処理もそのまま通しました（実際に動かして確認）。
  - HTML の解析の規則では、閉じていない `<a>` はその後の段落で作り直されます。その結果、照合の詳細やコメント欄など、本文より後ろの大部分がそのリンクの中に入ります。
  - 狙える筋書き：外から入った文を AI が本文に書く → 毛利さんがコメント欄などを押す → 偽の「ログインし直してください」画面でパスワードを取られる。
  - ボタンそのものは押せば元の動きをする見込みです。どこまでリンクになるかの細かい形はブラウザで確かめていないので、**推測**です。
- **直し方：** 除去処理で開いているタグを積み上げて覚え、対応の無い閉じタグは捨て、最後に開いたままのタグを全部閉じる。
  - あわせて、本文のリンクに `target="_blank" rel="noopener noreferrer"` を付ければ、レビュー画面そのものが入れ替わるのを防げます。

### 4. Low：IP の取り方に偽装の余地がある（推測）
**場所：** `review-auth.js:74`

- **何が起きるか：** `x-nf-client-connection-ip` が無いか、2 つあって `header()` が null を返すと、`x-forwarded-for` の先頭を使います。先頭は送る側が自由に書けるので、要求ごとに IP を変えて IP ごとの上限を逃れられます。
  - Netlify が利用者の送ったこのヘッダを消すかどうかは、公式の記載を見つけられませんでした。
  - IPv6 なら /64 の中で住所を変え続けられます。全体の上限は残ります。
- **直し方：** `x-forwarded-for` は使わない。IP が取れないときは固定の 1 つの区分（例：`unknown`）にまとめる。

### 5. Low：保存した IP のハッシュから元の IP を戻せる
**場所：** `review-auth.js:75`

- **何が起きるか：** 前に付ける文字列が公開されている SHA-256 なので、IPv4 の全部（約 43 億通り）を試せば、Blobs の鍵から元の IP が分かります。ログの 8 文字でもほぼ絞り込めます。指示書どおりの作りですが、「IP をそのまま残さない」というねらいは弱くなります。
- **直し方：** 元の秘密から HKDF で別用途の鍵を作り、HMAC にする。パスワードとは関係させないので、パスワードを変えても数は残ります。

### 6. Low：本文の外部の画像で、閲覧を外に知られる
**場所：** `review-auth.js` の CSP（`img-src ... https:`）と、`review-html.js:55`

- **何が起きるか：** AI が書いた本文に `<img src="https://攻撃者/p.gif">` があると、毛利さんがレビュー画面を開いた時刻と IP が攻撃者に伝わります。URL は `no-referrer` で漏れません。
- **直し方：** レビュー画面では `img-src 'self' data:` に絞るか、除去処理で外部の画像を落とす。

### 7. Low：`safeNext` が普通の URL まで捨てる
**場所：** `review-auth.js:41`

- **何が起きるか：** 文字列のどこかに `http` があるだけで捨てます。たとえば `ref=draft/http-...` やファイル名に `https` を含むテーマです。ログイン後に `/review`（400 の画面）へ移ってしまいます（動かして確認）。
- **直し方：** 制御文字・`\`・先頭の `//` と、`new URL` で origin と道筋を確かめる部分は残し、`http` を含むかどうかの広い確認は外す。

## 観点ごとのまとめ

| 観点 | 判断 |
|---|---|
| 認証の抜け | 問題なし。4 つの関数とも、認証の前にあるのはメソッドの確認だけです。GitHub への取得や書き込みは認証の後です。`_handler` は HTTP からは呼べません。 |
| Cookie・署名・鍵 | 問題なし。偽造・期限・パスワード変更での無効化・`__Host-` の条件・Cookie が 2 つある場合は、どれも正しく断ります。ログアウトはサーバ側でセッションを無効にしませんが、指示書どおりです。 |
| CSRF | 抜けは無し。ただし 1 の High で、正しいログインまで止まります。 |
| XSS | スクリプトが動く経路は無し。nonce・全項目のエスケープ・`scriptJson`・`javascript:` の符号化した形の除去を確かめました。指摘は 3 と 6 です。 |
| オープンリダイレクト | 問題なし（7 は表示の問題です）。 |
| 総当たり | 2 と 4 です。Blobs が使えないときに 503 で断る作りは正しいです。 |
| 情報の漏れ | 問題なし。ログ・応答・エラーにパスワード・Cookie・トークン・鍵は出ません（IP の扱いは 5）。 |
| 既存の動きの壊れ | 1 です。それ以外では、3 つの処理の中身と応答・ボタンの動きは同じです。既存の 277 件の記事に class・style 付きの生の HTML は無く、表示は変わりません。試験の手助けは本番のコードに抜け道を作っていません。 |

## 確かめた範囲

- 除去処理・`safeNext`・同時の失敗の数え方は、node で直接動かしました（ファイルは作っていません）。
- この作業場所には `node_modules` が無いため、試験一式は流していません。
- 管理画面の書き込みの関数は POST しか受けないので、本文の `<img src="/...">` から操作される心配はありません。

## マージしてよいか

**不可。** 1（High）を直し、ログインできることをブラウザで確かめた後なら可です。2 と 3 は直すか記録するかの扱いですが、どちらも直すのは小さな作業なので、同じ PR で直すことを勧めます。
