# 01 解析の修正

対象は `scripts/lib/tsutatsu-parser.js` と `scripts/lib/nta-tsutatsu.js` の2つ。

## A. 条番号として範囲表記を認める（`tsutatsu-parser.js`）

`PROVISION_NO_RE` を、要素に**1回だけ** `～` を許す形にする。

いまの形（`の`・`・`・`共` は既に許している）:

```
要素 = \d{1,3}(?:の\d{1,2})?(?:・\d{1,3}(?:の\d{1,2})?)*共?
全体 = ^要素(?:-要素){1,3}$
```

これを次のようにする:

```
素   = \d{1,3}(?:の\d{1,2})?(?:・\d{1,3}(?:の\d{1,2})?)*
要素 = 素(?:～素)?共?
全体 = ^要素(?:-要素){1,3}$
```

`共?` は範囲の**外側**に付ける。実際の表記が `181～223共-6`（`共` は範囲全体に掛かる）で、
`181共～223共` とは書かないため。

### 通ってほしいもの

```
181～223共-6     法第181条から第223条まで（源泉徴収）共通関係の第6項
23～35共-2
183～193共-1
194～198共-1
```

### 通ってはいけないもの

```
181～223共         枝番が無い（-N が必須）
～223共-6           左端が無い
181～～223共-6      波記号の連続
181～223～300共-6   1要素に範囲は1回だけ
```

### 既存の形は今までどおり通ること

```
37-13        所得税の一般形
6-4-5        消費税の一般形
37-14の2     枝番
12の5-1-1    章番号に「の」
1の3・1の4共-1  相続税の併記形
36・37共-1
194・195-1
```

## B. 波記号の表記ゆれを寄せる（`tsutatsu-parser.js`）

`normalizeProvisionNo` は全角ハイフンを半角に寄せているが、波記号は素通しになっている。

国税庁のページは **U+FF5E（全角チルダ `～`）**で統一されているので、カタログのキーは
必ず U+FF5E になる。一方、記事の本文や質疑応答事例の関係法令欄が
U+301C（`〜`）や U+007E（`~`）で書いてくると、**完全一致しないため未解決になる**。

`DASHES` と同じ要領で、`normalizeProvisionNo` の中で `[〜~]` を `～`（U+FF5E）に寄せること。
寄せ先は U+FF5E。カタログのキーがそちらだから。

> 注意：`nta-tsutatsu.js` の `CITATION_RE` は既に `[～〜~]` の3種を検出できる。
> 検出はできても照合で落ちる、という状態を無くすのがここの目的。

## C. 取りこぼしに気づけるようにする（`tsutatsu-parser.js` / `crawl-nta-tsutatsu.js`）

今回の件は「`<h2>` はあるのに条文が0件」という状態が**誰にも見えないまま**続いていた。
同じことを繰り返さないようにする。

`parseTsutatsuPage` が `looksLikeProvisionNo` で捨てたブロックを数えて返す。

```js
return { sectionTitle, provisions, skipped };
// skipped: [{ no, title }]  条番号として認められずに捨てたもの
```

`crawl-nta-tsutatsu.js` 側で、節ページごとに `skipped` が1件以上あれば警告を出す。

```
[warn] 条番号として読めない見出しを 16 件飛ばしました
       https://www.nta.go.jp/law/tsutatsu/kihon/shotoku/04/10.htm
       例: 23～35共-1 （公的年金等の複数回の支払）
```

既存の呼び出し側が `{sectionTitle, provisions}` を分割代入しているだけなら、
プロパティを足しても壊れない。壊れる箇所があれば直すこと。

## D. `findProvision` の照合順序（`nta-tsutatsu.js`）

PR #605 で `findProvision` は次の形になっている。

```js
const rangeStart = key.match(/^(.+?)[～〜~]/)?.[1];
for (const c of targets) {
  const p = provisions[key] || (rangeStart && provisions[rangeStart]);
  ...
}
```

これは「通達ごとに、完全一致 → 左端」の順で見ている。
カタログに範囲形のキーが1件も無かったので今まで問題にならなかったが、
**今回の変更でカタログに `181～223共-6` が入る**ため、順序を明示しておく。

**全通達で完全一致を先に試し、どこにも無ければ左端を試す**形にすること。

```js
// 完全一致を全通達で探す → 見つからなければ左端を全通達で探す
```

理由：`circular` を省略した呼び出し（`buildProvisionBlock` に文字列だけ渡した場合）で、
ある通達の「左端の一致」が別の通達の「完全一致」に勝ってしまうのを防ぐため。

なお `36-40～43`（条の範囲）の左端フォールバックは**残す**。
`181～223共-6` は完全一致で引けるようになるので、左端（`181`）には落ちない。

## 期待する挙動

```
looksLikeProvisionNo('181～223共-6')   → true
looksLikeProvisionNo('181～223共')     → false
normalizeProvisionNo('181〜223共－6')  → '181～223共-6'   // U+301C が U+FF5E に寄る
normalizeProvisionNo('181~223共-6')    → '181～223共-6'   // U+007E も同様

（カタログ再生成後）
findProvision('181～223共-6','shotoku') → 181～223共-6 の条文
findProvision('181〜223共-6','shotoku') → 同上（波記号違いでも引ける）
findProvision('36-40～43','shotoku')    → 36-40（左端。従来どおり）
findProvision('181-6','shotoku')        → 181-6（別物。従来どおり）
```
