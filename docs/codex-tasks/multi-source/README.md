# 論点ごとの出典 — 複数論点の記事が必ず「要修正」になる問題を直す

## 背景

日次生成の記事に、次の警告が毎回のように付く。

```
要修正（内容確認）
理由: 出典: LLM選定の確信度が低い（0.62 < 0.9）
```

2026-09-17 の本命記事「土地・家を生前贈与するには？」で出た警告。生成ログはこうだった。

```
[source] 税務の論点語: 不動産の贈与税評価額 / 相続時精算課税 / 暦年課税 / 登録免許税
[source] LLM選定(A) domain-fallback→llm-auto: No.4409 conf=0.62
理由=不動産の生前贈与で主要な論点となる贈与税の計算に直接対応する候補です。
     ただし、評価方法や登記費用、相続との比較全般を扱うページではありません。
```

**この記事は4つの論点を扱っている。** タックスアンサーは1ページ1論点の構成なので、1件で全体を覆えるはずがない。Luna（選定LLM）の 0.62 は正しい判断で、間違っているのは**問いの立て方**のほうだ。

今のガードはこう訊いている:

> 「No.4409 は "不動産の生前贈与" **全体** を覆っているか？」

複数論点の記事に対して、この問いには誰も答えられない。

直近12日の日次生成で LLM 選定が走った7件:

| Tier | 確信度 | 結果 |
|---|---|---|
| A | 0.62 | 要修正 |
| A | 0.72 | 要修正 |

| A | 0.86 | 要修正 |
| B | 0.55 | 要修正 |
| A | 0.92 | 通過 |
| A | 0.99 | 通過 |

**7件中5件（71%）が要修正。** 公開済みの `llm-auto` 記事12本を調べると確信度は全て 0.9 以上で、0.9 未満は一本も通っていない。つまり 0.9 未満＝必ず人手の手戻りが発生する。

### 出典は既に複数使われている

記事265本を調べた結果:

| | 件数 | 割合 |
|---|---|---|
| 本文にタックスアンサー番号を引いている | 235 | 89% |
| 本文で**2件以上**引いている | 101 | **38%** |
| frontmatter の正本**以外**も引いている | 108 | **41%** |

本文中の引用件数の分布: `1件:134 / 2件:50 / 3件:33 / 4件:14 / 5件:4`

実例:
```
正本=4103 | 本文=4103, 4408, 4152, 4124, 4158
正本=2200 | 本文=1350, 2200, 2080, 1900, 1191
```

さらに `citation-linker.js` がビルド時に本文中の「No.XXXX」を自動でリンクに変換している。**読者はすでに複数の出典に辿れる。**

1件に縛られているのは次の2箇所だけで、これは税務上の要請ではなく実装の都合である。

| 箇所 | 制約 |
|---|---|
| `templates/blog-post.html:67` | 記事末の「参考：」欄が1件しか出ない |
| `scripts/lib/source-alignment.js` | 承認ガードが `source_url` の1件だけを見る |

`scripts/build.js:587` のコメントにも、この制約を回避した跡が残っている:

> `frontmatter の source_url はテンプレートが1件しか表示しないため、これが無いと読者は社会保険側の出典に辿れない。`

## 何をするか

**出典を増やすのが目的ではない。問いを論点ごとに分解して、答えられる形にするのが目的。**

```
今:  「No.4409 は "不動産の生前贈与" 全体を覆っているか？」 → 0.62 → 要修正

後:  「不動産の贈与税評価額 → どのページ？」 → No.4602 conf=0.95 ✓
     「相続時精算課税       → どのページ？」 → No.4103 conf=0.97 ✓
     「暦年課税             → どのページ？」 → No.4408 conf=0.96 ✓
     「登録免許税           → どのページ？」 → No.7191 conf=0.93 ✓
     → 全論点に出典がある → 警告なし
```

論点語は**すでに生成時に取得済み**（`scripts/lib/tax-terms.js`、2〜4語）。新たに作る必要はない。今は出典探しの検索語として使い捨てているだけで、保存もしていない。

## 決まっている設計判断（変更しないこと）

### 1. 連番の平坦キーを使う。ネストした YAML リストは使えない

frontmatter の解析器がリポジトリ内に**7つ**あり、うち**6つは行単位の素朴な正規表現**でネストを読めない。

| 解析方法 | ファイル |
|---|---|
| gray-matter（本物の YAML） | `scripts/build.js:5` / `scripts/validate.js:11` / `scripts/lib/source-guard.js:3` |
| 素朴な正規表現（**ネスト不可**） | `netlify/functions/review-page.js:35`<br>`netlify/functions/admin-list-articles.js:36`<br>`netlify/functions/admin-change-article-status.js:37`<br>`scripts/generate-draft.js:1717`<br>`scripts/lib/site-corpus.js:31`<br>`scripts/lib/preflight-check.js:26` |

さらに `source-guard.js` の `restoreMissingSystemFields` は**1行を正規表現で抜き出して復元する**実装なので、複数行にまたがるブロックは復元できない。

```js
const line = (beforeFm.match(new RegExp('^' + key + ':.*$', 'm')) || [])[0];
```

JSON を1行に詰める案も却下する。`review-page.js` の正規表現が `([^"]*)` で最初の `"` で切れるため、JSON 中の `"` で壊れる。

**→ `source_2_url:` のような平坦な連番キーにする。** 退屈だが、7つの解析器すべてと行単位の復元処理の両方で正しく動く唯一の形。

### 2. 既存265記事は一切変更しない

連番キーが無い記事は、今までと同じ1件表示・1件判定のままにする。移行もマイグレーションもしない。

### 3. 選定ロジック（Tier と閾値）には触らない

`llm-source-selector.js` の `DEFAULT_MIN_CONFIDENCE`（0.5）と Tier A→B→C→D の打ち切り条件は**現状のまま**。ここを触る案は検討した上で見送っている。今回は `resolveSourceWithLLM` を**論点ごとに呼び分けるだけ**で、関数の中身は変えない。

### 4. 上限は4件（正本＋3件）

`tax-terms.js` の `parseTerms` が論点語を4語で打ち切っているため（`if (out.length >= 4) break;`）、論点は最大4つ。連番キーは `source_2_*` 〜 `source_4_*` の3組で足りる。

## 作業の単位

1. `01-selection.md` — 論点ごとの出典選定と frontmatter への記録
2. `02-guard-and-render.md` — 承認ガードの判定と、記事末の「参考」欄の表示
3. `03-tests.md` — テスト

## 守ってほしい前提

- **記事の自動公開・自動マージはしない。** 日次記事は毎日ユーザーが手でレビューして承認する運用。この変更は警告の出方を変えるだけで、公開フローには触らない
- **既存の挙動を壊さない。** 連番キーが無い記事（既存265本）は、今までと1文字も変わらない HTML を出すこと
- **出典を捏造しない。** 論点ごとの選定でも、候補リストにあるカタログ収録ページからしか選ばない（`resolveSourceWithLLM` が既にそうなっている）
- **確信度の閾値 0.9（`LLM_AUTO_MIN_CONFIDENCE`）は下げない。** 警告を減らすために基準を緩めるのは、この作業の目的ではない
