# 03 公開前の照合（記事の主張を原文で裏付ける関門）

背景は `README.md` の原因 5。本作業の中心。

## 全体の流れ（新しいモジュール `scripts/lib/fact-check.js`）

```
本文 ──R1 主張の抜き出し──▶ 主張の一覧
主張 ──R2 根拠の検索──▶ 主張ごとの根拠（原文の抜粋）
主張＋根拠 ──R3 判定──▶ 裏付けあり／食い違い／資料なし／期限の書き漏れ
判定 ──R4 修正──▶ 直した本文 ──R1〜R3 をもう一度（直した文と新しい文だけ）──▶ 最終結果
最終結果 ──R5 記録──▶ frontmatter・review_warning・recommendation（承認ゲート）
```

LLM を呼ぶ箇所（抜き出し・判定・修正）はすべて関数を差し替えられるようにする（テスト用）。

## R1 主張の抜き出し

- 本文（frontmatter を除く Markdown）から、次の種類を述べた文を抜き出す: `要件`（誰が・何が対象か、適用の条件）・`金額`（上限・控除額・税額）・`割合`（税率・みなし仕入率等）・`期限`（適用期限・申告や届出・申請の期限・保存期間）・`適用年`（いつから・何年分から）・`手続`（届出・申請・選択の要否）・`番号`（条文・通達・タックスアンサーの番号）・`判定`（〜なら〜になる、という結論）。
- 出力は JSON: `[{ id, sentence（本文の原文そのまま）, heading（見出し）, type, subject（制度名・論点名）, claim（主張を 1 文に要約）}]`。`sentence` が本文に実在しないものは捨てる（文字列照合）。
- 想定事例の中の数値（「想定」と明示された設例の金額など）は、税率・控除額などの制度の数値を使っている部分だけを対象にする。
- 上限は 1 記事 40 件（`FACT_CHECK_MAX_CLAIMS`）。超えたら `期限`・`要件`・`判定`・`金額`・`割合`・`手続`・`適用年`・`番号` の順で優先し、落とした件数を記録する。

## R2 根拠の検索（ローカルのカタログ全体から）

- 検索の対象: ① 生成時に渡した資料（`source_bundle`、01 R4）、② `data/nta-sources/`（タックスアンサー・質疑応答事例）、③ `data/nta-tsutatsu/`（通達）、④ `data/law-sources/`（法令・施行令）。
- 検索の手がかり: 主張の `subject` と `claim` の語、本文に書かれた番号（条・通達・TA 番号は既存の `checkCitations`・`findProvision`・法令の別名表で直接引く）、論点語の対応（既存の `resolveSourceForTopic`・`tax_terms` の仕組み）。語の一致は既存の `tokenizeQuery` など既存の部品を優先して使う。
- 主張ごとに最大 3 件、1 件 2,000 文字以内の抜粋（該当段落の前後）を返す。タックスアンサーは `law_version`（「令和〇年〇月〇日現在法令等」）を必ず添える。
- 検索は LLM を使わない（再現できて安いこと、テストできること）。

## R3 判定

- 判定は 1 回の LLM 呼び出しで、主張を最大 10 件ずつまとめて渡す。根拠が 0 件の主張は LLM に送らず「資料なし」。
- 判定の種類:
  - `裏付けあり` … 根拠の原文に同じ内容がある。根拠の該当文を `quote` に原文のまま書く。
  - `食い違い` … 根拠の原文と矛盾する（期限・金額・要件・対象・条の読み方が違う）。`quote` と `correct`（原文に基づく正しい内容）を書く。
  - `資料なし` … 根拠が無い、または根拠では判断できない。
  - `期限の書き漏れ` … 主張の制度について、根拠に適用期限があるのに本文のどこにも書かれていない（制度ごとに 1 件）。
- **`quote` が根拠の原文に文字列として含まれない判定は `資料なし` に置き換える**（根拠のでっち上げを防ぐ）。空白と全角半角の違いだけは揃えて比べる。
- 根拠が古い（`law_version` が今日から 1 年半以上前）ときは、`裏付けあり` でも `注意: 根拠の基準日が古い` を付ける。
- 判定の指示文には、「判断できなければ資料なしにする」「記憶で補わない」「括弧書き・ただし書きの対象を取り違えない」を入れる。
- モデルは `FACT_CHECK_PROVIDER` / `FACT_CHECK_MODEL`（既定 `anthropic` / `claude-opus-5-5`。GitHub の変数）。呼び出しは既存の `content-model.js` の仕組みを使う。書き手のモデル（`CONTENT_MODEL`）とは別に設定する。

## R4 修正

- 1 回の LLM 呼び出しで、次をまとめて最小限に直す（既存の `applyMissingRulesToBody` と同じ「該当箇所だけ直して全文を出す」方式・同じ出力形式の注意・本文短縮ガード）:
  - `食い違い` … 根拠の原文に合わせて直す（根拠の抜粋を添付する）。
  - `期限の書き漏れ` … その制度の説明に期限を 1 文で足す。
  - `資料なし` のうち種類が `要件`・`金額`・`割合`・`期限`・`適用年`・`手続`・`判定` のもの … 具体的な内容を外し、「詳しくは国税庁の〇〇で確認」程度の案内に置き換える（資料に無い具体を残さない）。`番号` の資料なしは番号を消して内容だけにする。
- 修正後の本文に、直した文と新しく増えた文だけを R1〜R3 にもう一度かける（1 回だけ。2 回目の修正はしない）。
- 修正の前後（文の対）を記録する。

## R5 結果の記録と承認ゲート

- frontmatter に追加（既存の項目は変えない）:
  - `fact_check_version: 1`
  - `fact_check_status`: `ok`（食い違い残 0）／`revise`（食い違いが残った、または期限の書き漏れが残った）／`not_run`（照合を実施できなかった）
  - `fact_check_summary`: 例「主張 32 件: 裏付けあり 24・修正 5（食い違い 3・期限 1・具体を外した 1）・資料なしで案内に変更 3・残った食い違い 0」
  - `fact_check_model`
- `fact_check_status` が `revise` か `not_run` のとき、`recommendation` を `revise` にする（既存の承認ゲートで承認できなくなる。差し戻しで直す）。`review_warning` に理由を足す（既存の内容は残す）。【要判断】2・3 の既定どおり。`FACT_CHECK_FAIL_OPEN=true` のときだけ `not_run` でも `recommendation` を変えない。
- 照合の詳細（主張・判定・根拠の抜粋・修正の前後）は、記事ファイルではなく `data/fact-check/<slug>.json` に書き、下書きの枝に記事と一緒にコミットする（`daily-draft.yml` の記事の枝作成ステップで、記事ファイルと同じ枝に追加する）。公開時に main へ入ってよい（監査の記録として残す）。
- 照合を止める変数 `FACT_CHECK_ENABLED=false` のときは `fact_check_status: not_run`・`fact_check_summary: 照合を無効にしています`。

## R6 レビュー画面

`netlify/functions/review-page.js` に「事実の照合」の欄を足す（`data/fact-check/<slug>.json` を下書きの枝から読む。無ければ「照合の記録なし」）:
- 状態（ok／revise／not_run）と要約。
- 「直した箇所」（前 → 後、根拠の抜粋とページ・条へのリンク）。
- 「資料が無く案内に変えた箇所」。
- 「残った食い違い」（あれば赤で。根拠つき）。
- 画面の文言は日本語。既存の欄の並びは変えず、「変更箇所」の欄の後に置く。

## R7 適用する経路

- 新規生成（`generateArticle` の最後、`applyMissingRulesToBody` と題名の確定の後）。
- 差し戻し再生成（`regenerateTargeted`・`regenerateSection`・`regenerateWithOpenAI`。`regenerateTitleOnly` は本文が変わらないので照合しないが、前回の結果を引き継ぐ）。再生成後に照合をやり直し、`fact_check_status` と `recommendation` を更新する（直れば `revise` を外す。ただし `recommendation` が照合以外の理由で `revise`/`reject` だった場合は元に戻さない。元の値を `fact_check_prev_recommendation` に控える）。
- 公開中の記事の更新案（`runRefreshMode`）。
- 2 本モード・`--force-slug` でも同じ。
- 0 本で終わる日は呼ばない。生成後の重複判定で取り下げる記事には照合しない（費用の無駄）→ 照合は重複判定の後に行う。

## R8 手動で照合するスクリプトとワークフロー

- `scripts/fact-check-article.js <記事ファイル> [--ref <枝>] [--write]`: 1 本を照合し、結果を標準出力と `data/fact-check/<slug>.json` に出す。`--write` が無ければ本文は直さない（照合だけ）。
- 手動ワークフロー `.github/workflows/fact-check.yml`（`workflow_dispatch`、入力: 枝名・記事ファイル。結果を Actions の Summary に出す。コミットしない）。受け入れ確認で #642〜#644 に使う。

## テスト（`scripts/lib/__tests__/test-fact-check.js`）

偽の LLM で流れを、実データで根拠検索を確かめる。

1. 抜き出し: 本文に無い `sentence` は捨てる。上限 40 件と優先順。想定事例の数値の扱い。
2. 根拠検索（実データ、LLM なし）: 次の主張で、正しい内容の原文が上位 3 件に入る。
   - 「結婚・子育て資金の一括贈与の非課税は令和8年3月31日までの拠出が対象」→ TA No.4511（「令和9年3月31日」を含む）
   - 「贈与税の配偶者控除は、居住しているか、その見込みがあればよい」→ 相続税法21条の6（「翌年三月十五日まで」を含む）
   - 「住宅取得等資金の贈与の非課税」→ TA No.4508（期限の記載を含む）
   - 「二世帯住宅は構造や出入口で判断が変わる」→ TA No.4124 または措令40の2
   - 「居住の用に供されなくなる直前の居住の用（措法69の4①）は建替え中の扱い」→ 措法69の4
   - 「届出がなければ売れ残り在庫を低く評価できない」→ 所基通47-22〜47-24 のいずれか
3. 判定: `quote` が原文に無い `裏付けあり` は `資料なし` になる。根拠 0 件は LLM を呼ばずに `資料なし`。古い基準日の注意。
4. 修正: 食い違い → 根拠つきで修正依頼が作られる。資料なしの `期限` → 具体を外す依頼。`番号` の資料なし → 番号を消す依頼。本文短縮ガードが効く。再照合は 1 回だけ。
5. 記録: `ok`／`revise`／`not_run` ごとの frontmatter・`review_warning`・`recommendation`。照合以外の理由の `revise` を照合の再実行で消さない。`FACT_CHECK_ENABLED=false`・`FACT_CHECK_FAIL_OPEN=true` の挙動。
6. 承認ゲート: `fact_check_status: revise` の下書きは既存の承認処理で 400 になる（既存のテストの形に合わせる）。
7. レビュー画面: 3 つの状態で欄が描画される（HTML の文字列で確かめる）。記録が無いとき。
8. 経路: 新規・差し戻し・更新案で照合が呼ばれ、取り下げた記事・`regenerateTitleOnly` では呼ばれない。

## 変更してはいけないもの

- 既存の品質ゲートの条件（`recommendation`・適合スコア）と承認処理の他の部分。
- 生成後の重複判定・論点別ルール・通達番号と条番号の照合の中身。
- `content/posts/*.md`。
