# 01 計画・制度ごとの資料・資料の記録・照合の段 A/B（第 1 段）

README の 1〜2 を先に読むこと。用語:

- **計画**: 書く前に、記事で扱う税の制度・論点の一覧（最大 8）を作ること。
- **計画の資料**: 計画の制度ごとに、カタログから引いたページ（最大 2）。
- **書き手の資料**: 書き手（本文を書く AI）への指示に添付した資料すべて（主出典・補助出典・計画の資料・Q&A・法令・通達・改正情報）。
- **段 A / 段 B**: 照合の判定を、まず書き手の資料だけで行い（段 A）、資料なしになった主張だけ今と同じ全体の検索で判定し直す（段 B）。

## P1 計画（新しい部品 `scripts/lib/article-plan.js`）

- `planSystems(topic, { generate })` を作る。`generate` の既定は `contentModel.generateSimple({ system, user }, { maxTokens: 2000 })`（本文と同じ提供元・モデル。Gateway では content-model 側の下限が効く）。
- 指示文（system）は次のとおり（試しで使った文。変えるときは理由を報告）:
  `税理士事務所のブログ記事の企画です。読者の疑問に答えるために本文で説明が必要な税の制度・論点を、必要なものだけ最大8つ挙げてください。制度の正式な名前に近い名前（国税庁のタックスアンサーの題名に近い言い方）にしてください。出力は JSON 配列だけです。形は [{"name":"制度名","why":"この記事で何を説明するか（30字以内）"}]。`
- user は企画の項目（`target_query`・`primary_question`・`search_intent`・`reader_problem`・`success_outcome`・`tax_terms`・`article_type`・`persona`）を `項目: 値` の行で並べたもの。
- 答えの読み方: 最初の JSON 配列を読む（コードの囲み・前後の文があってもよい）。`name` が文字列で、前後の空白を除いて 2〜40 字のものだけ採る。NFKC と全角・半角をそろえた形で重複を除き、先頭から 8 件まで。
- 戻り値は `{ status: 'ok', systems: [{ name, why }] }` か `{ status: 'failed', reason }`。呼び出しの失敗・読めない答え・0 件は `failed` にし、**例外を呼び出し元に投げない**。`reason` は固定の短い文（鍵や答えの本文を入れない）。
- 切り替え `FACT_PLAN_ENABLED`（既定 `true`。`'false'` のときだけ止める）。止めたときは計画も資料探しもせず、生成の指示・前付けを**今と 1 字も変えない**。

## P2 制度ごとの資料と関連の確かめ（`findSystemMaterials(systems, topic, options)`）

- 探す範囲: いまの `evidenceCatalog()`（タックスアンサー・質疑応答・法令・通達）**＋国税庁 Q&A**（`data/nta-qa/index.json` の各問。id は URL、種類 `qa`、題名は `資料名 問の題名`、本文は各ファイルの `body`）。改正情報（`tax-law-changes` の `CHANGES`）は今どおり `getChangesForTopic` で添付し、計画の検索には入れない。
- **照合の段 B の検索（`searchEvidence` のカタログ）には Q&A を足さない**（既存の検索の試験・基準値を変えないため）。
- 名前と本文は NFKC と全角・半角をそろえてから比べる（「２割特例」と「2割特例」を同じに読む）。制度名の本体は `subjectWithoutTrailingParens`（`fact-evidence.js` の内部関数。export して使ってよい。中身は変えない）で末尾のかっこを外した形。かっこの中身（4 字以上）は別名として使ってよい。
- **関連の確かめ（必須）**: 次のどれかを満たすページだけを候補にする。どれも満たさないページは、検索の点が高くても採らない。
  1. 題名に制度名の本体か別名を含む。
  2. 本文（タックスアンサーは「関連リンク」より前）に制度名の本体か別名をそのまま含む。
  3. 制度名の本体から一般的な語（税目名・「制度」「特例」「場合」「非課税」など、実装で一覧にする）を除いた語が、すべて題名に含まれる（例:「贈与税の配偶者控除」→「配偶者」「控除」が「夫婦の間で居住用の不動産を贈与したときの配偶者控除」に含まれる）。
- 並べ方: 題名が当たるもの → 本文に名前が多く出るもの → いまの検索の点。種類はタックスアンサー・質疑応答・Q&A を法令・通達より先にする（法令・通達は題名が当たるときだけ）。制度ごとに最大 2 ページ。
- 1 ページの本文は、タックスアンサーは「関連リンク」の前まで、6,000 字以下なら全文、それより長ければ制度名の出る位置の付近（`contiguousExcerpt` に `focus` で制度名を渡す等）を 6,000 字まで。
- 全体の上限: 新しく添付する本文の合計 60,000 字・18 ページ（主出典など既存のブロックに既に載る資料は数えない）。超える分は後ろの制度から落とし、落とした制度は「資料なし」扱いにはせず計画の記録に「上限で添付せず」と残す。
- どのページも関連の確かめを通らなかった制度は **資料なし**（`missing`）にする。
- 戻り値: `[{ name, why, materials: [{ id, kind, title, url, text }], missing: boolean }]`。

## P3 書き手への指示

- 日次の生成（`generateWithContentModel`）で、計画が `ok` のとき、既存の資料のブロック（`ntaRefsBlock` 等）の後に次のブロックを足す。
  - 見出し `═══ この記事で扱う制度と資料 ═══`、`扱う制度: A、B、…`、`資料が見つからなかった制度: X、…（この制度は名前と「詳しくは国税庁の〇〇で確認」程度の案内までにする）`。
  - 計画の資料のうち、既存のブロックにまだ載っていないものは `【資料】題名 / URL` と本文を添付する。既に載っているもの（主出典・補助出典・Q&A のブロック・法令・通達のブロック）は本文を重ねず `（上に掲載）題名` と書く。
  - 規則（この 3 つ）:
    1. 税の要件・対象者・金額・割合・期限・適用年・届出や申請・判定の基準・条文や通達の番号は、添付した資料（このブロックと上の資料）に書いてあることだけを書く。あなたの記憶にある税制は古い可能性が高い。
    2. 「資料が見つからなかった制度」は、名前と案内までにする。
    3. 「扱う制度」に無い制度について、要件・金額・期限などの具体を書かない。
- 計画が `failed` のときはこのブロックを付けず、今と同じ指示で生成する。
- 第 1 段では文ごとの資料番号は付けさせない（第 2 段）。
- 出典が未確定（`isSourceUnconfirmed`）の題材でも、計画と資料探しは行い、ブロックを付ける。【要判断】未確定の題材の既存の規則（特定のページを「〜によれば」と根拠に挙げない）は残す。食い違うと判断した場合は、未確定の題材ではブロックを付けない実装にして報告すること。

## P4 書き手の資料の記録

- 前付けに次の項目を足す（`draft-normalizer` の雛形と、計画が `ok`/`failed` のとき。`FACT_PLAN_ENABLED=false` のときは足さない）。
  - `fact_plan_status`: `ok` / `failed`
  - `fact_plan`: 制度名を ` ／ ` でつないだ文字列
  - `fact_plan_missing`: 資料が見つからなかった制度名（同じ形、無ければ空）
  - `fact_materials`: 書き手の資料の id を `;` でつないだ文字列。主出典・補助出典・計画の資料・Q&A のブロックに載せた問・法令と通達のブロックの条・改正情報（`getChangesForTopic` で添付したもの）を含める。参考ページ・税以外の出典など、カタログの id で引けない資料は含めなくてよい。
- id は短い形にする: タックスアンサー `ta:<番号>`、質疑応答 は URL（またはカタログの id）、法令 `law:<key>:<num>`、通達 `tsutatsu:<circular>:<no>`、Q&A `qa:<source_key>/<id>`、改正情報 `change:<key>`。`materialId(ref)` と、id から `{ id, kind, title, url, text }` を返す `resolveMaterial(id)` を作り、すべての種類で往復できるようにする（改正情報の本文は `title`＋`summary`＋`reference`）。
- レビューの注意書き（`review_warning`）に、資料なしの制度があれば `計画: 資料が見つからない制度 X・Y`、計画が `failed` なら `計画を作れませんでした（従来の資料だけで生成）` を足す。
- **差し戻し（`regenerate*`）・更新案（`runRefreshMode`）**: 記事の前付けに `fact_plan_status: ok` と `fact_materials` があれば、計画の AI を呼ばずに、記録の制度名と id から P3 のブロックを作り直して添付する。その経路で新しく添付した資料（本文が引いている通達など）は `fact_materials` に足す。前付けに無い記事（古い下書き・公開済み記事）は今と同じ。新しい項目は再生成の後も消えないこと（`finalizeRegeneration`・`inheritFactMetadata`・`recordMaterialMetadata` の流れを確かめる）。

## P5 照合の段 A / 段 B（`scripts/lib/fact-check.js`）

- `articleEvidenceOptions(meta)` で `fact_materials` を読み、`writer_materials`（id の配列）として渡す。
- 切り替え `FACT_CHECK_WRITER_MATERIALS`（既定 `true`。`'false'` のときだけ止める）。`writer_materials` が空・切り替えが止まっているときは**今と全く同じ**照合（呼び出しの内容・回数・記録の形。既存の試験の期待を変えない）。
- 書き手の資料があるとき:
  - **段 A**: 主張ごとの候補を、書き手の資料だけから選ぶ。並べ方はいまの `searchEvidence` の点の付け方を書き手の資料に限って使い、上位 4 件。修正後の再照合で必須の根拠（今の `required`）は先頭に入れる。抜粋と資料表の作り（`contiguousExcerpt`・`buildPages`・`pageGroups`）、判定の指示文、確認は今と同じ。
  - **段 B**: 段 A の結果が資料なし（候補なし・答えなし・確認で落ちたものを含む）の主張だけ、今と同じ `searchEvidence`（全体の検索、必須の根拠を先頭）で判定し直し、その主張の結果を段 B の結果に置き換える。段 A で裏付けあり・食い違い・期限の書き漏れになった主張は段 A の結果のまま。
  - 段 B は Batch の設定にかかわらず**即時**で呼ぶ（件数が少なく、Batch の待ちをもう 1 回増やさないため）。記録の `calls[]` に `stage_b_judge`（再照合では `recheck_stage_b_judge`）として残す。
  - 「判定の答えの多くが確認を通らない」歯止め（`checkTally`）は、**段 A・段 B の最終的に採った答え**で数える（段 A で落として段 B で判定し直した主張は段 B の答えで数える）。段 B だけの少ない件数で照合全体を `not_run` にしないこと。全体で多くが落ちる場合は今どおり止める。
  - 修正後の再照合も同じ段 A / 段 B で行う。
  - 主張の上限: 書き手の資料がある記事は、`FACT_CHECK_MAX_CLAIMS` が未設定なら要件・判定・手続を 80 件（数字の上限 120 件は今のまま）。書き手の資料が無い記事は今のまま 40 件。
  - 記録: 主張ごとに `stage: 'A' | 'B'`。`record.writer_materials` に id の数と内容の指紋（並べた id の sha256 の先頭 16 字）、`record.stages = { A: { claims, pages, input_chars }, B: { … } }`。要約の文の末尾に `・書き手の資料で判定 N 件・全体を探した M 件` を足す。
- `LOGIC_VERSION` を `plan1` に上げる。差し戻しで前回の記録を使い回す条件に、書き手の資料の指紋が同じことを足す。
- 照合のモデル・effort・Batch（段 A 以外）・指示文・確認・修正・止める範囲・`max_tokens` は変えない。

## P6 ワークフロー（env の行を足すだけ）

- `daily-draft.yml`・`regenerate-draft.yml`・`refresh-article.yml` の生成の手順に `FACT_PLAN_ENABLED: ${{ vars.FACT_PLAN_ENABLED }}`。
- 照合を行う手順（上の 3 本と `fact-check.yml`・`audit-published-facts.yml`）に `FACT_CHECK_WRITER_MATERIALS: ${{ vars.FACT_CHECK_WRITER_MATERIALS }}`。
- `fact-check.yml` の「照合のコードとカタログを取る」の取り出し一覧に `data/nta-qa/` を足す（Q&A の id を本文に引けるように）。
- それ以外の行（`run:` の中身・権限・入力）は変えない。`test-workflow-change-detection.js` の期待は変えない（未コミットの間は落ちる試験なので、Codex は流さなくてよい）。

## P7 試験（新しい試験ファイル `scripts/lib/__tests__/test-fact-plan-01.js`。偽の LLM、ネットワークなし）

1. `planSystems`: 正しい配列・コードの囲みつき・読めない答え（`failed`）・0 件（`failed`）・9 件以上（8 件まで）・全角と半角の重複（1 件にまとまる）・呼び出しの例外（`failed`、例外を投げない）。
2. `findSystemMaterials`: P2 の表の実例をカタログ全体で確かめる。どのページも関連の確かめを通らない架空の制度名で `missing: true`。全体の上限で落とした制度の記録。
3. 書き手への指示: 計画 `ok` で P3 のブロックが付く。主出典の本文が指示の中に 2 回出ない。資料なしの制度の文。計画 `failed` で、ブロックなし・注意書きあり。
4. `FACT_PLAN_ENABLED=false`: 生成の指示（promptIR）と前付けが、この変更の前と 1 字も違わない（変更前の組み立てと突き合わせる）。
5. 前付けと id: `fact_plan*`・`fact_materials` が書かれる。`materialId`/`resolveMaterial` がタックスアンサー・質疑応答・法令・通達・Q&A・改正情報で往復する。主出典・補助出典・Q&A のブロックの問・法令の条・改正情報が `fact_materials` に入る。
6. 差し戻し: `fact_plan_status: ok` の記事で、計画の AI を呼ばずにブロックが付き、項目が再生成の後も残る。項目の無い古い記事は今と同じ。
7. 照合（書き手の資料あり）: 段 A の偽の LLM に渡る資料表が書き手の資料だけ。段 A で資料なしの主張だけが段 B に回り、段 B は全体の検索の候補で、Batch の設定でも即時。段 A の裏付けあり・食い違いは段 B に回らない。
8. 照合の歯止め: 段 B だけ見ると `checkTally` に当たるが、全体では当たらない例で `not_run` にならない。全体で多くが落ちる例は今どおり `not_run`。
9. 照合（書き手の資料なし・切り替えを止めたとき）: 呼び出しの内容と記録が今と同じ（既存の照合の試験がそのまま通ること）。
10. 上限: 書き手の資料ありで 80 件、なしで 40 件、`FACT_CHECK_MAX_CLAIMS` があればそれ。
11. 修正後の再照合: 必須の根拠が段 A の候補の先頭に入り、資料なしなら段 B に回る。
12. 記録: `stage`・`record.writer_materials`・`record.stages`・要約の文・`LOGIC_VERSION`。指紋が違う記録を差し戻しで使い回さない。

既存の試験の期待は、この変更で必ず変わるもの（`LOGIC_VERSION` の文字列など）だけを最小限直し、どれをなぜ変えたか報告する。確かめを弱める方向に変えない。

## P8 変更してはいけないもの

- 照合の判定の指示文・引用の実在確認・数字の歯止め（前後 300 字）・候補の外の資料の扱い・期限の書き漏れ・修正の指示文と保全条件・止める範囲・承認の差し止め・fail-closed。
- 書き手の資料が無い記事の照合（呼び出し・記録・結果）。公開済み記事の一括照合（`audit-published-facts`）の結果。
- 照合のモデル・effort・Batch（段 A と抜き出し・修正）・`max_tokens`。
- `searchEvidence` の候補・並び・抜粋（段 B と書き手の資料が無い記事で使う。Q&A を足さない）。
- 本文の生成のモデル・長さの扱い・論点別ルール・既存の資料のブロックの中身と順番（P3 のブロックを後ろに足すだけ）。
- `content/posts/*.md`・`data/`・`docs/codex-tasks/fact-grounding/fixtures/`。ワークフローは P6 の行だけ。
