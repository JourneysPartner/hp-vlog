# 11b 鮮度 第 2 段階: レビュー指摘の修正（2026-10-01）

`11-freshness-p2.md` の実装に対するレビュー（Claude Opus 5.5 xhigh）で見つかった問題を直す。作業ツリーにある 11 の実装の上に重ねる。11 の「変更してはいけないもの」はそのまま有効。

## F1 承認の作りを変える（指摘 1・2・3 の根本対策）

今の作り（下書き枝のファイルを書き換えてから PR をマージする）は、次の問題を起こす。
- マージに失敗すると、印の消えたファイルが枝に残る。承認し直すと通常の承認経路に入り、記事が消えて公開日が変わる。
- 差し戻しで frontmatter が崩れると、そのまま公開中の記事に入る。

次の作りに改める。

### 承認（`review-approve-background.js` の更新案の経路）

1. **判定**: 更新案かどうかは、`refresh_of: "published"` の印**または** `ref` が `draft/refresh-` で始まることで判定する。どちらか一方でも更新案の経路に入れる。
2. **元にするファイル**: 枝のファイルと main のファイルを読む。main が `published` でなければ断る（今のまま）。
3. **チェックの対象**: 出典ガード・仮置き題名・recommendation とスコアの判定は、**main のファイルの frontmatter**（`review_status` は `published`）で行う。反映後の frontmatter は main のものだからである。
4. **反映する内容**: main のファイルの frontmatter を一字も変えずに使い、`updated_at` と `reviewed_at` だけを現在時刻（JST）にする。本文は枝のファイルの本文を使う。改行コードは main のファイルに合わせる。
   - 本文が main と同じ（NFKC 正規化と空白除去のあとで比べる）なら、何も書かずに断り、「反映する変更がありません」と通知する。
5. **書き込み**: その内容を `putFile` で **main に直接**書く。コミットメッセージは `refresh: <題名> (#<PR 番号>)`。sha の競合なら main を読み直して 4 から 1 回だけやり直す。
6. **後始末**: 書き込みが成功したら、PR を閉じ（`closePR`）、枝を消す（`deleteBranch`）。どちらも失敗しても成功扱いのまま、ログだけ残す。**枝のファイルは、成功するまで一切書き換えない**（失敗しても同じ経路でやり直せるようにするため）。
7. **通知**:
   - 成功時は `refresh_published` を送る。
   - 失敗時（断った場合と例外）は `refresh_failed` を理由つきで送る。承認はバックグラウンド関数なので、応答の 400・500 は誰にも見えないため。
   - 枝が読めず、PR も開いていない場合（二度押しで処理済みなど）は、`refresh_failed` ではなく「この更新案は処理済みか、取り下げられています」という短い通知にする。
8. **使わなくなる部分**: マージ関係（`waitForMergeable` / `mergePR`、マージ後の確認）は更新案の経路から外す。
9. **関数の公開の仕方**: `exports.handler` は `(event) => handler(event)` にする。Netlify が渡す第 2 引数（context）を差し替え用の引数と取り違えないため。テストからは `_handler` を使う。

### 通常経路の安全弁（`review-approve-background.js`）

`ref` があり、main に同じファイルがあって `review_status` が `published` なら、通常経路では何も書かずに 409 で止める。ログを残し、通知は送らない（二度押しや、古い枝の事故を防ぐ）。新しい記事の承認（main にファイルが無い）は今までどおり。

### レビュー画面（`review-page.js`）

- 更新案かどうかは、印**または** `ref` の接頭辞で判定する（承認と同じ規則）。
- 案内文に「反映されるのは本文だけです。題名・要約・公開日・出典欄は公開中の記事のまま変わりません。」を足す。
- 「変更箇所」は、**main の本文**と**枝の本文**を比べる（今のまま）。

### 差し戻し（`generate-draft.js --regenerate` で、更新案の場合）

- 分類が全文再生成（`full`）なら targeted に切り替える。
- 分類が題名だけ（`frontmatter`）なら、何も変えずに警告を付ける。警告の文面は「更新案では題名・要約は変えられません。題名の変更は別の作業で行います。」とし、今の「自動反映できなかった」と同じ通知の流れに乗せる。
- 再生成のあと、frontmatter は**再生成前の枝のファイルのもの**をそのまま使う。変えるのは本文と、再生成が通常変える `review_status` / `review_comment` だけ。そのため、`restoreSourceGuardFields` などによる出典項目の追加は、更新案には入らない。

### 管理画面の「確認済み」（`admin-freshness-action.js`）

次の場合は 409 で断る（「更新案の作成中、または更新案があります」）。
- 枝 `draft/refresh-<slug>` がある（GitHub API の ref 取得で確かめる）。
- `refresh-article.yml` の実行が `queued` か `in_progress`（`listWorkflowRuns`）。

開いている PR の確認は、`findPR(branch)` のように head を指定して 1 本だけ見る（先頭 100 件だけ読む方式をやめる）。管理画面の一覧で使う PR の取得も、ページ送りで全件読む。

## F2 変わっていない節に触らない（指摘 4）

- `runRefresh`（`--refresh`）では、手順ごとの出力を節に分け、段落の並び（前後の空白を除いたもの）が元と同じ節は、**元の本文の文字列をそのまま使う**。最終的な本文は、元の本文のうち書き換わった節の範囲だけを差し替えたものにする。変わっていない部分は 1 バイトも変えない（見出し直後の空行・末尾の空白・改行コードを含む）。
- `diffSections` は、節が変わったかどうかを段落の並び（前後の空白を除く）で判定する。空白だけの違いは変更に数えない。
- 差し戻しの再生成でも同じ差し込み方をする。

## F3 小さな修正

1. **PR 本文の警告（指摘 5）**: `writePullRequestBody` → `buildPullRequestBody` に `expiredTheme` を渡し、期限切れの警告を PR 本文に出す。
2. **`GITHUB_OUTPUT` の書き方（指摘 6）**: `generate-draft.js` と `freshness-workflow.js` の出力は、区切り文字を使う書き方（`key<<DELIM` … `DELIM`）にし、`%25` などの置き換えをやめる。区切り文字は値に含まれないランダムな文字列にする。
3. **警告の見落とし（指摘 7）**: 再生成の出力が `review_status: "needs_revision"` になっていたら、`review_comment` の行が無くても `failed` にする。
4. **見出しの合わせ方（指摘 8）**: 理由の `where` が `###` 以下の見出しなら、本文の中でその見出しの親に当たる `##` の節を対象にする。`where` が「本文」や導入部なら、targeted の手順にする（指示文は同じ文面で、「この節」を「本文」に読み替える）。`refreshable` は `buildRefreshPlan` の結果が空でないことで決める（候補の生成と計画で条件をそろえる）。
5. **別サイトからの操作を防ぐ（指摘 9）**: `admin-freshness-action.js` は、`Content-Type: application/json` でない POST を 415 で断る。`Origin`（無ければ `Sec-Fetch-Site`）が `https://mori-zeirishi.net` と同じでない場合は 403 で断る。`Origin` も `Sec-Fetch-Site` も無い場合は断る。管理画面の送信側は今の `fetch` のまま通ること。
6. **指示文に見出しを入れる**: section の指示文の先頭を「「{見出し}」の節には…」「「{見出し}」の節の制度に関係する…」とし、見出しが見つからず targeted に切り替わっても、どの節の話か LLM に伝わるようにする。それ以外の文面は 11 のまま。
7. **作業語の判定**: `findInternalProcessWords` で失敗にするのは、元の本文より出現回数が増えた語があるときだけにする。

## テスト（追加・書き換え）

### 承認

- 印が消えた枝（`ref` は `draft/refresh-…`）でも更新案の経路に入る。
- 反映内容が「main の frontmatter ＋ 枝の本文」で、`updated_at` と `reviewed_at` 以外の frontmatter が main と 1 バイトも違わない。
  - 枝の frontmatter の題名・`publish_at`・出典項目が崩れていても、main には入らない。
- main に直接書き、PR を閉じて枝を消す。マージ関数を呼ばない。
- `putFile` が失敗したとき、枝のファイルを書き換えていない。`refresh_failed` が届く。
- sha 競合では 1 回だけやり直す。
- 本文が同じなら書かずに断る。
- 二度押しのときは、処理済みの通知になる。
- 通常経路では、main が `published` のファイルを 409 で止め、何も書かない。新しい記事の承認は今までどおり。
- `exports.handler` に第 2 引数を渡しても、本物の GitHub 関数を使う（偽の context で確かめる）。

### 差し戻し

- 全文再生成の分類が targeted になる。
- 題名だけの分類は警告で止まる。
- 出典項目や日付が変わらない。

### 本文の差し込み

- 変わっていない節が 1 バイトも変わらない。見出し直後に空行がある記事・CRLF の記事で確かめる。
- `diffSections` が空白だけの違いを数えない。

### そのほか

- 管理画面: 枝がある・実行中の場合に「確認済み」が 409。Content-Type 違いは 415、他サイトからの送信は 403。今の画面からの送信は通る。
- 計画: `###` の見出しから親の `##` を探す。「本文」の場合は targeted になる。計画が空なら `refreshable` が false。
- `GITHUB_OUTPUT`: `%` や改行を含む値が、そのまま読み戻せる。
- PR 本文に期限切れの警告が出る。

## 変更してはいけないもの

11 と同じ。特に、通常の下書きの承認・見送り・差し戻し・予約公開の挙動（追加するのは「main が published なら 409」の安全弁だけ）と、`content/posts/*.md`。
