# 国税庁Q&A の本文に目次が紛れ込む

## 何が起きているか

国税庁Q&A のクローラが、まとめ PDF を「問」ごとに切り分けるとき、
**答が書かれた本文の代わりに、巻頭の目次の行を拾うこと**がある。

```
keigen/jirei-52  コンビニエンスストアのイートインスペースでの飲食

  正しい本文（707字）
    （コンビニエンスストアのイートインスペースでの飲食） 問52 店内にイートインスペースを
    設置した…【答】 イートインスペースを設置しているコンビニエンスストアにおいて、例えば、
    トレイや返却が必要な食器に入れて飲食料品を提供する場合などは、店内のイートインスペースで
    飲食させる「食事の提供」であり、軽減税率の適用対象となりません（消法２①九の二、
    別表１一イ、基通５－９－９⑶）。…

  目次を拾ったとき（222字）
    （コンビニエンスストアのイートインスペースでの飲食） 問52 店内にイートインスペースを
    設置した…ますか。 【令和５年 10 月改訂】 ······························· 22
```

**すでに本番のデータに2件混入している**（`keigen/gaiyo-14` 241字・`keigen/jirei-42` 133字）。
2026-09-09 のクロール結果（PR #592）では**17件**に増えていた。マージしていれば
イートイン・テイクアウト・有料老人ホームなど21件の答えが失われていた。

この本文はそのまま記事生成のプロンプトに渡るので、答えの無い断片を根拠として渡すことになる。

## 原因

`scripts/crawl-nta-qa.js` の `splitByQuestion`（軽減税率Q&Aが使う）のガードが、
同じファイルにある他の2つの分割関数より弱い。

```js
// splitByQuestion（いま）
if (body.length < 120) continue;
if (/…{3,}|\.{6,}\s*\d+$/.test(body)) continue;
```

```js
// splitByNumberedHeading（暗号資産）
if (!/問/.test(body) || !/答/.test(body)) continue;   // 目次には答が無い
if (body.length < 150) continue;

// splitByParenQuestion（相続）
if (!/（答）|【回答要旨】|【回答】/.test(body)) continue;
if (body.length < 150) continue;
```

弱い点は2つ。

**1. 答を求めていない。** 他の2つは本文に「答」があることを確かめている。
`splitByQuestion` だけ確かめていない。目次には答が無いので、これだけで大半は防げる。

**2. 点線の判定が実際の文字と合っていない。** 国税庁の PDF が使っているのは
**`·`（U+00B7 MIDDLE DOT）**。いまの正規表現は `…`（U+2026）と `.`（U+002E）しか見ておらず、
`·` にはかからない。

```
jirei-52 の末尾: "【令和５年 10 月改訂】 ······················ 22"
                                            ↑ すべて U+00B7
```

長さ 222字は 120 の下限を超えるので、長さでも止まらない。

なお、同じ問が目次と本文で2回出たときは長い方を採る仕組みが入っている。
それでも漏れるのは、**抽出のたびに語順が変わり、本文側の見出しが正規表現に
当たらない回がある**ため。PDF のテキスト抽出（pdftotext）は実行ごとに読み順が変わる。

## やること

1. `splitByQuestion` のガードを他の2つに揃える（[01-guard.md](01-guard.md) の A）
2. 点線の判定に実際の文字を入れる（同 B）
3. **取り込み時に、既にあるレコードの本文が大きく短くなる更新を拒む**（同 C）
   — 1と2で防げない未知の失敗にも効く、最後の砦
4. 既に混入している2件を落とす（同 D）
5. テスト（[02-tests.md](02-tests.md)）

## やってはいけないこと

- `splitByNumberedHeading`・`splitByParenQuestion` の既存のガードを緩めない
- `data/nta-qa/` を手で編集しない。データの直しはクローラの実行で行う
- 記事ファイル・公開フロー・承認フローに触らない
- pdftotext の呼び出し方を変えない（読み順の非決定性そのものは今回直さない）
