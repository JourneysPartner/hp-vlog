## 1. 仕様の目的・背景

### 1-1. 目的
- 国税庁の質疑応答事例（推定 3,000〜5,000 件）を、読者に近い「想定事例」として一般化した記事の生成を可能にする
- 現状のタックスアンサーベース記事だけではカバーしきれない**実務的なエッジケース・業種別具体例**を網羅する

### 1-2. 解決する問題
- 現状の記事は基本ルール解説が中心で、業種別・取引別の具体例が薄い
- 国税庁の質疑応答事例は良質な実務論点を提供するが、転載は法的・SEO 的に NG
- 「論点だけ借りて読者向け事例に置換」する標準パターンを確立したい

### 1-3. スコープ外
- 質疑応答事例の自動 crawl（別仕様：Phase C 国税庁ソース DB 構築）
- Phase 3 Fact-Check の本実装（別仕様：プラン (b) の Fact-Check 設計）
- 既存記事の遡及リライト

## 2. `docs/article-generation-rules.md` の改定方針（既存章への溶込型）

ChatGPT の元提案を「末尾に章 21 として追加」せず、**既存の関連章に溶け込ませる**形で改定する。改定対象章と内容：

### 2-1. セクション 3（記事タイプ）への追記
質疑応答事例ベース記事の article_type 位置づけを既存セクション内に追記：
- 既存 7 タイプはそのまま使う
- `source_type` フラグで「質疑応答事例ベース」を識別
- 質疑応答事例ベース記事は通常 `case_study` / `edge_case` / `misconception_fix` / `industry_example` のいずれかになる
- 推奨構成（想定事例 → 判断 → 実務対応）は **既存タイプの必須要素 + Q&A 固有の追加要素**として定義（詳細はセクション 2-8）

### 2-2. セクション 7（出典・根拠の引用ルール）の全面改定
現状の優先順位リストを **「ソースごとの役割分担表」** に置き換える：

| 出典 | 主な用途 | 引用スタイル | 過去誤記検知への寄与 |
|---|---|---|---|
| **タックスアンサー** | 基本ルール解説、納税義務判定、閾値説明、原則の根拠 | 直接引用可、要約可 | **原則必須**（基本ルール照合の主役）|
| **質疑応答事例** | エッジケース判断、業種別具体例、想定事例の論点抽出 | **本文転載禁止**、論点と判断軸のみ参考 | 補完（基本ルールは載っていない）|
| **法令・通達** | 条文番号で根拠を示す補強 | 条文番号で引用、条文本体の長文転載は避ける | 中 |
| **国税庁パンフレット・FAQ** | 最新情報・改正内容の補強 | 出典明記して要点引用可 | 補完 |

**運用ルール（GPT 補足5 反映で柔軟化）**：
1. **原則として、タックスアンサーで基本ルールを補強する**
2. **対応するタックスアンサーが見つからない場合は、法令・通達・国税庁 FAQ・パンフレットのいずれかで基本ルールを補強する**
3. **質疑応答事例のみを単独根拠にしない**
4. 基本ルール（特定期間の AND/OR、新設法人特例、輸出免税の扱い等）は **タックスアンサー優先**

### 2-3. セクション 8（数値ハルシネーション防止）への追記
質疑応答事例ベース記事固有の注意：
- 想定事例で変えた金額（売上規模・取引金額等）が結論に効く場合、必ず元事例での閾値を別途明示する
- 例：元事例「課税売上 3 億円」で結論「特定新規設立法人非該当」、置換先「課税売上 8,000 万円」の場合、両者の差が結論に効く点を明記

### 2-4. セクション 14（文体・トーン）への追記
- 質疑応答事例ベース時：**事実関係を変えた場合は断定しない**（「このような整理になる可能性があります」「個別判断が必要です」を使う）

### 2-5. セクション 15（禁止事項）への追記
質疑応答事例ベース記事に特有の禁止事項を追加：
1. 質疑応答事例の本文を長く転載する（**連続 3 文以上の同一文字列禁止**）
2. 照会内容・回答内容をほぼそのまま記事化する
3. 国税庁の回答を、変更後の想定事例に当てはめて断定する
4. `source_url` なしで質疑応答事例ベースの記事を生成する
5. 事実関係が違うのに「国税庁ではこう回答しています」と断定する
6. 古い法令や改正前の取扱いを、現在も有効であるかのように書く
7. 実在の個別納税者・個別企業を連想させる事例にする
8. 不安を煽りすぎる表現
9. 税理士への相談を過度に強制する表現
10. 「必ず」「絶対」「すべての場合」などの断定の乱用
11. 記事内の見出しに「照会要旨」「回答要旨」を使わない

### 2-6. セクション 16（記事末尾テンプレート）への追記
質疑応答事例ベース記事の **免責文追加文言**（通常の免責文の直後に追加）：

```
国税庁の質疑応答事例は、一定の事実関係を前提とした考え方を示すものです。実際の税務判断は、契約内容・金額・時期・当事者関係などにより異なる場合があります。
```

### 2-7. セクション 17（frontmatter）への追加フィールド（GPT 補足1・2 反映）

**`source_type === "nta_shitsugi"` の場合、以下を条件付き必須にする**：
- `source_url`：主たる質疑応答事例の URL
- `source_title`：主たる質疑応答事例のタイトル
- `case_based: true`
- `case_transformed: true`
- `case_transform_note`：置換内容のメモ
- `source_tax_category`：元事例の税目

**通常記事では上記すべて optional のまま**（後方互換性確保）。

**補助出典の管理（複数参照する場合）**：
- 主たる出典 → `source_url` / `source_title`
- 補助出典 → `supporting_source_urls`（配列、URL のみ）または `source_refs`（配列、URL + タイトル）
- 初期実装で複数出典メタの仕組みが間に合わない場合は、**本文内に補助出典の URL を記載**するか、内部 DB 側で保持する

frontmatter 例：
```yaml
source_type: "nta_shitsugi"
source_url: "https://www.nta.go.jp/law/shitsugi/.../01.htm"
source_title: "（元事例のタイトル）"
source_tax_category: "消費税"
case_based: true
case_transformed: true
case_transform_note: "EC セラー向け想定事例として一般化、業種と金額を置換"
supporting_source_urls:
  - "https://www.nta.go.jp/taxes/shiraberu/taxanswer/shohi/6501.htm"
  - "（法令データベース URL 等）"
```

### 2-8. セクション 18（記事構造テンプレート）への追加（GPT 補足8 反映で軽量化）

**質疑応答事例ベース記事の構造は「必須 6 + 任意 3」**：

**必須セクション（6 個）**：
1. **この記事でわかること・結論**
2. **今回の想定事例**
3. **元事例との差分**（GPT 補足4 反映で 3 項目に分けて記述）
4. **判断のポイント**（このケースで問題になる税務上のポイント + なぜその結論になるのか）
5. **実務で確認すべきこと**（契約書・請求書・入金日・領収書・登記簿・相続関係資料・残高証明・支払調書 等）
6. **免責文**（通常 + 質疑応答事例ベース追加文言）

**任意セクション（3 個、SEO・問い合わせ導線の観点で必要に応じて）**：
7. **似ているけれど結論が変わりやすいケース** ← **SEO・誤判断防止の観点で強推奨**
8. **よくある誤解**
9. **税理士に相談すべきライン**（過度に不安を煽らない）

**「元事例との差分」セクションのフォーマット（補足4 反映）**：

固定文「結論に効く部分は変更していません」は使わない。毎回、以下の 3 観点を分けて書く：

```markdown
## 元事例との差分

【変更した点】
- 業種：◯◯（元事例は△△）
- 金額：◯◯万円（元事例は△△億円）
- 取引時期：◯◯（元事例は△△）

【変更していない点】
- 税目：消費税
- 判断軸：反復・継続性
- 適用要件：◯◯

【結論に影響する可能性がある点】
- 元事例は売上規模が大きく特定新規設立法人の論点があったが、本記事の想定事例は売上規模が小さいため該当しない可能性がある
- 結論が変わる可能性があるため、断定的な表現は避けて記述する
```

**テンプレート全体**（軽量版）：

```markdown
---
（frontmatter、source_type=nta_shitsugi で条件付き必須項目あり）
---

## この記事でわかること・結論

（結論先出し）

この記事では、国税庁の質疑応答事例を参考に、読者に近い形へ一般化した想定事例として解説します。実際の取扱いは事実関係により異なるため、個別判断が必要です。

---

## 今回の想定事例

（業種・金額・時期・当事者・取引形態を読者に近づける）

---

## 元事例との差分

【変更した点】
- ...

【変更していない点】
- ...

【結論に影響する可能性がある点】
- ...

---

## 判断のポイント

（税目・判断軸・どの事実が結論に効くか・なぜその結論になるのか）

---

（任意：似ているけれど結論が変わりやすいケース／よくある誤解 を必要に応じて）

---

## 実務で確認すべきこと

（契約書・請求書・入金日 等、テーマに応じて具体化）

---

（任意：税理士に相談すべきライン）

---

本記事は情報提供を目的として作成しており、特定の税務判断を推奨するものではありません。実際の税務処理・申告については、税理士等の専門家にご相談ください。個別事情によって結論が異なる場合があります。

国税庁の質疑応答事例は、一定の事実関係を前提とした考え方を示すものです。実際の税務判断は、契約内容・金額・時期・当事者関係などにより異なる場合があります。

---

（ペルソナ別 CTA + 事務所案内）
```

## 3. 想定事例への置換ルール

### 3-1. 変更してよい要素
業種 / 取引金額 / 取引時期 / 売上規模 / 家族構成 / プラットフォーム / 事業形態 / 契約形態 / 支払方法 / 資産の種類 / 読者ペルソナ

### 3-2. 変更してはいけない要素（結論を左右する重要事実）
税率 / 期限 / 控除要件 / 適用要件 / 居住者・非居住者 / 課税・非課税 / 事業所得・雑所得 / 消費税の課税・不課税・非課税・免税 / 相続税・贈与税の適用要件

### 3-3. 置換が結論を変えうる場合の扱い
- 断定しない（「このような整理になる可能性があります」「個別判断が必要です」と書く）
- 元事例と異なる事実を足した場合、「国税庁ではこう回答しています」と書かない
- 「今回の想定事例」セクションのあとの「元事例との差分」で **3 観点（変更した点・変更していない点・結論に影響する可能性がある点）を分けて明示する**

### 3-4. ペルソナ別の置換例

| 元事例の論点 | 現実的な置換先 |
|---|---|
| 趣味で保有していた資産の譲渡が事業か | フリマセラーが個人コレクション（カード・コイン・古本）をまとめ売り |
| 同上 | 副業 EC セラーが廃業時の在庫を一括譲渡 |
| 親事業者と下請事業者の負担金精算 | ASP・広告代理店とクリエイターの広告制作費の立替精算 |
| 法人の役員報酬の損金算入 | 同族会社（夫婦経営の美容室・サロン）における役員報酬 |
| 居住用財産の譲渡所得 | 副業セラーの自宅兼倉庫の売却 |

## 4. n-gram 転載検知（validate への組込み）（補足3 反映）

### 4-1. 初期実装の仕様
- 記事の `source_url` から国税庁ページの本文を取得（Phase C で構築する DB から）
- 国税庁原文と記事本文をそれぞれ文単位（「。」「？」「！」区切り）に分割
- **連続 3 文以上の完全一致** → **FAIL** （validate 不合格、生成記事は draft 化時にブロック）
- **短い定型文（1 文 10 文字未満）は除外**（「課税対象となります。」のような決まり文句の誤検知を避ける）
- 全角・半角の正規化後に比較

### 4-2. 将来拡張
- **50 文字以上の長文一致** → warning（連続 1 文でも）
- **高類似文の検知**（編集距離・コサイン類似度ベース）→ warning

### 4-3. 警告文
- FAIL 時：`✗ 国税庁原文との 3 文以上の連続一致を検出 — 転載リスク。記事を書き直すこと（n-gram 検知）`
- warning 時：`⚠ 国税庁原文との長文一致を検出 — 表現を変えることを推奨`

### 4-4. 実装依存
- Phase C（国税庁ソース DB 構築）完了が前提
- 単独実装は不可能、Phase C 完了後に着手

## 5. topic-pool への自動抽出 + 手動採用フラグ（補足7 反映）

### 5-1. 仕組み
Phase C で crawl した全質疑応答事例（推定 3,000〜5,000 件）に対し、スコアリングスクリプトで自動評価し、上位 N 件を候補リストに投入する。手動採用フラグ `adopted: true` のものだけ daily-draft で実際に使う。

### 5-2. スコアリング基準（暫定、実データで再評価）
- **ペルソナ適合度**：既存 6 ペルソナのカテゴリと一致するか（+30 点）
- **検索ニーズ推定**：タイトル中のキーワード（「経費」「課税」「贈与」等）の有無（+20 点）
- **改正・廃止リスク**：注記の「令和 X 年現在の法令」が直近 3 年以内か（+10 点）
- **判断の曖昧さ**：「総合的に判断」「事実関係による」等、想定事例化の余地があるか（+15 点）
- **タックスアンサーで補強可能性**：関連タックスアンサー番号と連携できるか（+25 点）

満点 100 点で、**70 点以上を候補化**。

### 5-3. 安全網（手動採用フラグ）
- 抽出後の topic を user / レビュアーが目視確認できるよう、`data/nta-shitsugi-topics-candidate.json` に書き出す
- daily-draft で実際に使う前に、`adopted: true` フラグを手動で立てる
- これにより「自動の量 + 手動の質チェック」を実現

| 7 日間の上限 | **2 本** |
| 同一税目の連続避け | 連続 3 ペアで同じ税目の Q&A はしない |

実装：
- daily-draft の selector で `source_type` を確認しながら topic 候補を選択
- 「直近 N 日で 質疑応答事例ベース記事が M 本」のキャップをコード上で enforce

## 8. 残課題（実装時に詰める）

1. n-gram の **FAIL 運用ポリシー**（記事を完全に書き直すか、警告のまま draft 保留にして人間レビュー必須化か）
